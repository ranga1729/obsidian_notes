A process represents a running program. 
It's the abstraction through which memory, processor time and I/O resources can be managed and monitored. 

Each process has,
1. Memory address space
2. A set of  kernel data structures
The kernel tracks every process in data structures like **process tables.**
(Process table are implemented in linux with `task_struct`).
![[task.jpg]]
The kernel maintains, 
- Address space map
	Which parts of memory belong to code, stack, heap, shared libraries, etc.
- Current status
	Process status(running, sleeping, stopped, zombie, etc)
- Execution priority
	Used by the scheduler to decide process gets CPU time. 
- Resource usage
	CPU time consumed, memory usage, I/O operations. 
- Open files and network ports
	The process can read/write data.
- Signal mask
	Which signals are blocked(ex: ignoring `SIGINT`)
- Owner
	The user who owns the process.

##### Components of a process,
- **PID(Process ID)**
	A unique number linux gives every process.
- **PPID(Parent Process ID)**
	The process that started the current process. 
	Ex: The shell is usually the parent of the command you run.
	Every process(except the first one `init`/`systemd`) has a parent process. 
	Helps track process hierarchy. 
- **UID(User ID)**
	the real user who started the process. 
	Ex: `nano` : UID = you
- **EUID(Effective User ID)**
	The ID that process is actually running as. 
	Important for permission.
	Ex: `sudo nano` : UID: you, EUID = 0(root)
- **GID/EGID(Group ID/Effective Group ID)**
	Same as EUID. Determines group-level access to files. 
- **Niceness**
	A value that influence process scheduling priority.
	Range: -20(highest priority) to +19(lowest priority)
	Ex: `nice -n 10 myscript.sh` 
- **Control Terminal**
	If the process is started from a terminal, this records the terminal that controls it. 
##### The Life Cycle of a process,
![[Pasted image 20250910140148.png]]
1. **Creating a new process**
In linux, every process is created by another process. 
To create a process, a process calls the `fork()` system call. 

> [!NOTE] `fork()`
> - It duplicates the parent process(the "parent") with a new PID.
> - The result is two almost identical processes.

***Question:** Since the child process is almost identical to the parent process, and the parent process ran the `fork()` function to create child process, child must also have  `fork()` running. Then how the kernel distinguish which one is child and which one is parent ?*
***Answer**: Even though the new child and parent both run the same process, the inside `fork()` function behaves differently. `fork()` is designed in a with a convention to identify these two.* 
*This convention is,*
- *Parent's `fork()` returns the child's PID(a positive number).*
- *Child `fork()` returns 0.*

2. **Replacing process code**
After  a process is created with `fork()`, the child process is just a copy of the parent which runs the same program as it's parent. 
To run a new program, it uses the `exec` family of system calls. (ex: `execl`, `execv`, `execvp`,...)

> [!NOTE] `exec` family
> - It replaces the current process's code, data and stack with a completely new program. 
> - The PID(process ID) stays the same, but the program inside changes. 

**The role of init/systemd**,
All processes in linux must have a parent. 
At boot, the very first process started by the kernel is init(in older systems) or systemd. This process becomes the ancestor of all other processes.
Even if a parent process dies, its child isn't left alone,the init/systemd process adopts the orphaned process. 

This ensures there's always a "chain of responsibility" for process management. 

3. **Process terminating and waiting**
When a process finishes, it doesn't vanish immediately. 
Instead it enters a "zombie" state. 

> [!NOTE] zombie state
> - The process is dead, but its entry still exists in the process table.
> - This entry stores information like the process's exit status. 

Then, the **parent must acknowledge the child's death** by calling `wait()` or `waitpid()`.
Once the parent calls `wait`, the kernel removes the zombie entry from the process table. 
	If the parent never calls `wait`, the zombie remains.
	If the parent dies without calling `wait`, the `systemd/init` will "reap"(clean up) the zombie. 

`Systemd/init` ultimately supervising everything. 

##### Process Signals
A signal is a software interrupt delivered by the kernel to a process. 
Each signal has a number(integer ID) and a name(ex: `SIGNIT`).
Process can,
- Catch the signal(handles it with the custom code)
- Ignore it(some signal can not be ignored)
- Be determine by it(default action)

Common signals,

|Signal|Name|Meaning / When Sent|Default Action|Catchable|Ignorable|Dumps Core|
|---|---|---|---|---|---|---|
|HUP|SIGHUP|Terminal hangup / reload config|Terminate|Yes|Yes|No|
|INT|SIGINT|Ctrl+C / interrupt|Terminate|Yes|No|No|
|QUIT|SIGQUIT|Ctrl+\ / quit|Terminate|Yes|No|Yes|
|KILL|SIGKILL|Force kill|Terminate|No|No|No|
|BUS|SIGBUS|Invalid memory access|Terminate|No|No|Yes|
|SEGV|SIGSEGV|Segmentation fault|Terminate|No|No|Yes|
|TERM|SIGTERM|Polite terminate request|Terminate|Yes|Yes|No|
|STOP|SIGSTOP|Pause process|Stop|No|No|No|
|TSTP|SIGTSTP|Ctrl+Z / terminal stop|Stop|Yes|No|No|
|CONT|SIGCONT|Continue a stopped process|Continue|Yes|Yes|No|
|WINCH|SIGWINCH|Terminal window size change|Ignore|Yes|Yes|No|
|USR1|SIGUSR1|User-defined signal 1|Terminate|Yes|Yes|No|
|USR2|SIGUSR2|User-defined signal 2|Terminate|Yes|Yes|No|

Above process signal names are in two styles, 
1. Official name
	Used in the source code, defined in the `<signal.h>` in C.
	The prefix `SIG` stands for signal.
Ex:
```c
#include <signal.h>
kill(pid, SIGHUP)
```
2. Shell-friendly name
	Shorter name used in command line tools.
	Ex: 
		`HUP` : `SIGHUP`
		`INT` : `SIGINT`
		`TERM` : `SIGTERM`
		`KILL` : `SIGKILL`
Usage example,
```sh
kill -HUP <pid>
```

##### Threads
Process is essentially a running instance of a program.
Processes are isolated form each other. One process can not directly access the memory of another process. 

A thread is the smallest unit of execution within a process. 
Threads exist inside a process and share most of the process's resources such as,
- Memory space(code, data, heap)
- Open files and sockets
Each thread has its own,
- Thread ID(TID)
- Stack
- Registers/program counter

Multiple threads within the same process can run concurrently and communicate easily because they share memory. 
Thread are lighter than processes because creating a thread doesn't require duplicating memory space. 

A process in linux can have states like,
- Running(R)
	Either executing on the CPU ready to run(runnable).
	Runnable : Waiting for the CPU to be scheduled
	In this state, a process is actively doing work or can be scheduled immediately. 
- Sleeping
	Waiting for an event(S) or resource(D).
- Stopped(T)
	Process execution is stopped. 
- Zombie(Z)
	Has finished execution but still has an entry in the process table.
	Zombie process do not use CPU or memory. 
- Dead/Terminated
	The process is completely cleaned up by the kernel.
	Rarely seen because it's quickly removed from the process table. 
- Other states(Idle, Paging, ...)

The overall process state is determined collectively for all its threads. 
	If  process is suspended, all its threads are effectively suspended. 
	If a process is runnable, at least one thread is ready to run on the CPU. 
Ex: 
	Process P has 3 threads: `T1`, `T2`, `T3`
	If  `T1` is running and `T2`, `T3` are waiting for I/O, the process may still be considered runnable because `T1` can execute. 

Runnable threads are ready to run, but sometimes the kernel has to do something first, 
- Completing disk I/O
- Resolving network requests
- Allocating memory
Until this background work is done, the thread cannot actually run on the CPU, even though it it "Runnable" in the system's view. 

If all threads in a process are in sleep state, the system reports the entire process as sleeping. 
Ex: 
	Process P has 3 threads: `T1`, `T2`, `T3`
	`T1` : waiting for disk read
	`T2` : Waiting for network response
	`T3` : Waiting for user input
	All threads are sleeping --> Process P is now sleeping.
	If any of above threads is runnable, whole process considered runnable.

#### Process monitoring
Here  are the commands used to monitor processes,

1. `ps` : Show all static list of running processes at the moment of execution.
```sh
ps  #List processes for the current shell
ps aux #Lists all processes with details
ps -ef #Full-format listing of all processes
ps -u username #Processes of a specific user
```
![[Pasted image 20250911133752.png]]
Columns,
- `USER` : Username of the process owner
- `PID` : Process ID
- `%CPU` : CPU usage
- `%MEM` : Memory usage
- `VSZ` : Virtual size of the process
- `RSS` : Resident set size(number of pages in memory)
- `TTY` : Control terminal ID
- `STAT` : Current process status(R for runnable, S for sleeping, ...)
- `TIME` : CPU time the process has consumed 
- `COMMAND` : Command name and argument

2. `top` : Real-time monitoring(refreshes automatically)
```sh
top
```
Useful commands inside,
- `P` : Sort by CPU usage
- `M` : Sort by memory usage
- `K` : Kill a process by PID
![[Pasted image 20250911134902.png]]

3. `htop` : Interactive `top`(enhanced)
```sh
htop
```
![[Pasted image 20250911135347.png]]

4. `pidof` : Find process ID of a running program
```sh
pidof chrome #returns PID of google chrome
```
![[Pasted image 20250911135650.png]]

5. `nice` & `renice` : Adjust process priority
`nice`
	Start process with a specific priority.
	Default = 0
	Range = -20(highest) to 19(lowest)
```sh
nice -n 10 ./myprogram #Start a process with lower priority
```

`renice` 
	Change priority of a an existing process.
Ex:
Lower the priority
```sh
renice 10 -p 1234 #lower the priority of PID 1234
```
Increase the priority(requires root)
```sh
sudo renice -5 -p 1234
```
Change the priority of all process of a user
```sh
renice 5 -u ramod #all processes of user ramod have nice value 5
```

6. `strace` : Trace system calls
Monitor what  a process is doing internally. 
```sh
strace -p 1234 #show system calls made by process ID 12345
```

#### Runaway Processes
A runaway process is a process that consumes excessive system resources(CPU, memory, disk I/O, etc) usually because of,
- A buggy program(infinite loop, memory leak, etc)
- A process that is stuck waiting or retrying operations endlessly. 
- A user accidentally starting multiple instances of a heavy program.

Load average(seen in `uptime` or `top`) shows the average number of processes waiting for CPU(or I/O) over the last 1,5 and 15 minutes.
![[Pasted image 20250911145106.png]]
If you have $N$ CPU cores,
- $\text{Load average} \le \text{N}$  --> System can keep up
- $\text{Load average} \ge \text{N}$ --> System overloaded

If there's a suspicious program runs in, you can monitor it's system calls using `strace` command. 

#### Periodic Processes
a periodic process is a process that runs at regular intervals or according to a schedule. 
They are triggered by some scheduler(like `cron` or `systemd`)

Ex usage:
- Backups every night at 2 AM
- Cleaning `/tmp` every week
- Running a monitoring script every 5 minutes.

Schedules can be created using,
1. `cron` command
2. `systemd` timers

###### 1. `cron` command (Traditional scheduler)
`cron` is the classic linux scheduler for running periodic tasks.
It uses `crontab` files that defines when to run a command. 

To edit a user's `crontab` file,
```sh
crontab -e #this will open the crontab file using a text editor
```

`cron` commands uses a specific syntax,
```python
* * * * *  command_to_run
│ │ │ │ │
│ │ │ │ └── Day of week (0–6, Sunday=0)
│ │ │ └──── Month (1–12)
│ │ └────── Day of month (1–31)
│ └──────── Hour (0–23)
└────────── Minute (0–59)
```

Ex:
```sh
#run every day at 2AM
0 2 * * * /usr/local/bin/backup.sh

#run every 5 minutes
*/5 * * * * /home/user/check.sh

#run every Monday at 9 AM
0 9 * * 1 /usr/local/bin/report.sh
```

To list cron jobs,
```sh
crontab -l
```
The daemon `crond` runs in the background and checks crontab. 

###### 2. `systemd` Timers(Modern Alternative to cron)
Newer linux systems(using `systemd`) support timers as an alternative to cron. 
They are unit files(`.timer` + `.service`) managed by `systemd`.

Advantages over cron,
- Can depend on other services.
- Logs go into `journalctl`
- More flexible(calendar events, monotonic timers, boot-time offset)

Ex: 
We want to run `/usr/local/bin/backup.sh` daily at 2 AM.

Step 1 : Crete a service unit : `/etc/systemd/system/backup.service`
```ini
[Unit]
Description=Daily Backup

[Service]
ExecStart=/usr/local/bin/backup.sh
```
Step 2 : Create a timer unit file : `/etc/systemd/system/backup.timer`
```ini
[Unit]
Description=Run backup daily at 2 AM

[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true

[Install]
WantedBy=timers.target
```
- `OnCalendar=_-_-_ 02:00:00` → every day at 2 AM
- `Persistent=true` → runs missed jobs at next boot

Step 3 : Enable and start the timer
```sh
sudo systemctl enable backup.timer
sudo systemctl start backup.timer
```
Step 4: Check timer
```sh
systemctl list-timers
```
