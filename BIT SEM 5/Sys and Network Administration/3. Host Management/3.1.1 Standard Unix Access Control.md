In linux, **"Everything is a file."**
Not just documents and photos, but also hardware devices like hard drive(`/dev/sda`), your mouse and even processes are represented as special files usually in the `/dev` directory. 

Because of this representation, kernel can use the standard file permission system to control who has access to it. 

### Access control for files
When accessing a file in linux, the systems needs to who is asking the permission. 
1. **Owner**
	Every file and director has an owner, usually the user who creed it. 
	The owner has the most control(besides root).
	The system keeps track on users by **"UID"**(User Identification Number) like `1001`.
2. **Group**
	Every file also belongs to a group. 
	This is a way to give access to multiple users at once. 
	Ex: `developers` group.
	The system keeps track on groups by **"GID"**(Group Identification Number).
3. **The superuser(root)**
	A special user with UID 0. 
	This is the system administrator thus it can bypass all permission checks and act as the owner of any file or process.

Every file and directory is owned by one user and one group. 

For every file, there are three basic permissions.

| Permission | For a file                | For a directory                           |
| ---------- | ------------------------- | ----------------------------------------- |
| Read(r)    | View content              | List content of the directory(using `ls`) |
| Write(w)   | Modify or delete the file | Create, rename, delete files              |
| Execute(x) | Run the file              | Enter the directory(using `cd`)           |
The permissions are set for three distinct categories of users, 
1. Owner
2. Group
3. Others

To check the permission of a file,
```sh
ls -l
```
Output will be something like,
```sh
drwxr-xr-- 1 student developers 4096 Aug 28 15:00 MyProject
```
`d` : it's a directory. For a regular file it would be `-`
`rwx` : Permissions for the owner(student).
`r-x` : Permissions for the group(developers).
`r--` : Permissions for others.
### Access control for process
Like files, every running process has an owner.
Usually the owner is the user who started the process. 
Ex: If you open a web browser, you are the owner of that browser process.

Ownership of a process give specific rights,
1. **Sending Signals**
A "Signal" is a way for the OS to communicate with a process. 
Ex: 
Run this command to kill a process. 
```sh
kill <process_id>
```
This command sends a `SIGTERM`(terminate) signal to that process. 
The owner can kill processes.

2. Reducing Scheduling Priority
The CPU is usually switch between hundreds of processes.
The **Scheduler** decides which process gets to run at any given moment. 
**Priority** tells the scheduler how important a process is. 
The owner can reduce the priority and it's called making a process "nicer".
- Regular users can lower the priority of their own processes. They can't increase it as it can cause a security or stability issues. 
- Only `root` can increase a process's priority. 

A process have three identities,
1. **Real UID(RUID)**
This is the ID of the user who launched the process. 
Ex: If you logged in as `student`, and run a process, the real UID is `student`'s UID.
2. **Effective UID(EUID)**
This is who the process is acting as right now. 
This is the ID, the kernel checks when determining if the process has permission to access a file. 
For 99% of your process `Real UID = Effective UID`
3. **Saved UID(SUID)**
This is a backup copy of the effective UID, used in special cases. 

###### Use case of having different UIDs(classic example of changing password)
The `passwd` lets you change your password.
Encrypted passwords are stored in th file `/etc/shadow` owned by the `root` and only be written by the `root`.

The `passwd` program has a special permission but called `setuid`.
1. When a non-root user(student) run the `passwd` command.
	Real UID = `student` (one who runs the process)
	The process start with an Effective UID = `root` (the one who owns the file)
2. When it need to write your new password to `/etc/shadow`, the kernel checks its Effective UID. It's root, so it grants permission.
3. The Saved UID 'remembers' this special root privilege. This allows the program to temporarily drops its root powers(by setting it effective UID back to the Real UID) to perform a non-privilege task and then restore them later to finish it job. 
#### SetUID & SetGID

SetUID(Set User ID) and SetGID(Set Group ID) are special permissions that can be set on an executable file. 
These IDs allows executable files to run with elevated permission. 
It works as a identity substitution system where a process temporarily takes on the identity of the file's owner or group, rather than the user who runs it. 

Normally, when you run a command:
- Your User ID becomes the process's **Real UID** and **Effective UID**.
- The kernel checks the **Effective UID** for permissions.

But, when you run a program that has the **SetUID bit** set:
1. You, the user, execute the file.
2. The kernel sees the SetUID permission on that file.
3. The kernel creates the process. Your user ID still becomes the **Real UID**.
4. However, the kernel sets the process's **Effective UID** to be the ID of the **owner of the file**.

We can see this special permission bits for the `passwd` program using,
```sh
ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 63736 Jan 20 2024 /usr/bin/passwd
```
Notice the `s` where the owner's execute permission (`x`) would normally be. This indicates that the SetUID bit is set.
First(`-`) is there to indicate that this is a file, not a directory.
