#### Drawback of standard access control
- If an attacker comprises root, it's a single point of failure. 
- `setuid` programs are potential vulnerabilities. 
	Standard UNIX doesn't let you split root's privileges. (ex: let user x only manage networking and nothing else)
	Solution is `setuid` programs. (programs that run with root's privileges even when launched by a normal user).
	Ex: `/bin/ping` is often `setuid` root, so regular users also can send ICMP packets.
	If there's a bug `setuid` programs, attackers can exploit it to gain root. 
- The traditional UNIX model was designed for standalone systems, not modern networked systems. 
	They doesn't natively support network-aware privilege separation.
	Attackers can exploit weak network services. 
- Only root can create or modify groups. 
- In the standard model, many security decisions are hardcoded into individual commands/daemons. 
	Security policies are scattered across many programs. 
	Hard to audit. 
	If one daemon is miss-configured, it's a threat. 
- Traditional UNIX doesn't log root operations. 
#### Extensions to the standard model
1. PAM : Pluggable Authentication Modules
2. Kerberos : Network cryptographic authentication
3. File system access control lists
4. Linux capabilities
5. Linux namespaces
##### 1. PAM : Pluggable Authentication Modules
![[Pasted image 20250903173419.png]]
PAM is a flexible framework for authentication. 
Instead of hardcoding how authentication works into each program, PAM provides a set of shared modules used for,
- Local login (`login`, `su`, `sudo`)
- Remote login (`ssh`, `ftp`)
- Services (like `cron`)
You can configure PAM to use passwords, smartcards, biometrics or LDAP(Lightweight Directory Access Protocol). A service doesn't need to know the details. 
This makes authentication **centralized and extensible**.
##### 2. Kerberos : Network cryptographic authentication
![[Pasted image 20250903174040.png]]
Kerberos is a network authentication protocol using cryptography. 
Instead of sending passwords across the network, users and services prove their identity using **ticket** issued by a trusted **Key Distribution Center(KDC)**.
Prevents password sniffing and replay attacks. 
Provides **secure single sign-on (SSO)** for distributed systems.

Widely used for,
- Distributed systems
- Large linux clusters
##### 3. Filesystem Access Control Lists(ACLs)
Traditional UNIX file permissions are set to,
- Owner
- Group
- Others
with `rwx` notation.
This is little bit rough. 
Instead, ACLs allow fine-grained permissions for multiple users and groups on a single file or directory. 

Ex:
```sh
setfactl -m u:alice:r file.txt #alice has read access
setfactl -m u:bob:rw file.txt #bob has read/write access
```
This can be stored as extended attributes on filesystems like (`ext4`, `XFS`).
##### 4. Linux Capabilities
Roots power can be split into smaller pieces that can given to processes individually. 
Ex: 
- `CAP_NET_ADMIN` : Manage network interface
- `CAP_SYS_BOOT` : Reboot the system
- `CAP_SHOWN` : Change file ownership
So a program doesn't need to be fully root, it can be granted the specific capabilities it needs. (Principle of least privilege)
##### 5. Linux Namespaces
A core feature behind containers(like dockers).
Namespace isolate system resources for processes. 
Types,
- **PID namespace** : separate process trees
- **NET namespace** : Separate network interfaces and routing tables.
- **MNT namespace** : Separate mount points(filesystems)
- **UTS namespace** : Separate hostname/domain
This allows multiple "virtual" environments to coexist securely on the same host. (Foundation for process isolation and containerization).
