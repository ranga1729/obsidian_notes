#### SQL Injection Attacks
- SQLi is an attack that exploits a sec vulnerability in the database layer of an application. 
- Using this, attackers can extract or manipulate the web application's data. 
- Reasons,
	1. Incorrectly filtered string literals 
	2. weakly typed user inputs 
	in embedded SQL statements. 
- SQLi is done by terminating a text string and appending a new command.

```python
var ShipCity;
ShipCity = Request.form("ShipCity");
var sql = "select * from OrdersTable where ShipCity = ' " + ShipCity + " ' ";
```
The intention of this code is to retrieve data from the Orders table filtered with the user given ship city name. 
Generated query will be,
```sql
SELECT * FROM OrdersTable WHERE ShipCity = 'Redmond'
```
What if the user enters this,
```txt
Boston' DROP table OrdersTable--
```
Now the query will be,
```sql
SELECT * FROM OrdersTable WHERE ShipCity = 'Redmond'; DROP table OrdersTable--
```
- Main reason for SQLi attacks is because developers have used insecure coding practices.
- Countermeasures,
1. Manual defensive coding practices
	Perform pattern matching and filter our abnormal user inputs.
2. Parameterized query insertion
	Allows developers to specify the structure of an SQL query. Unsanitary user inputs won't modify the query structure. 
3. SQL DOM
	A set of classes that enables automated data type validation and escaping.
	Uses encapsulation of database queries to provide a safe and reliable way to access databases.

- SQLi detection methods,
	1. Signature based: Attempts to match specific attack patterns. 
	2. Anomaly based: Define normal behavior and then detect behavior patterns outside the normal range. 
	3. Code analysis: Use a test suite to detect SQLi vulnerabilities. 
#### Database Access Control
- DBMSs support a range of administrative policies including,
	1. Centralized administration: Small number of privileged users may grant and revoke access rights.
	2. Ownership based administration: The owner(creator) of the table may grant and revoke access rights to the table
	3. Decentralized administration: Table owner can grant and revoke access right to the users and then users can grant and revoke access right to other users. 

- SQL provide two commands for managing access rights. 
	`GRANT` & `REVOKE`

**GRANT**
- Used to,
	1. Grant one or more access rights 
	2. Assign a role to an user.
Syntax
```sql
GRANT privilege_name
ON object_name
TO { user_name | PUBLIC | role_name }
[WITH GRANT OPTION];
```
- Privilege name: SELECT, INSERT, UPDATE, DELETE, ALL PRIVILEGES
- Object name: table, view, schema, function, procedure
- PUBLIC: Grants the privileges to all current and future database users.
- `[WITH GRANT OPTION]`: An optional clause that allows the recipient user or role to further grant the same privileges to other users.
Ex:
```sql
GRANT SELECT ON customers TO Jdoe;
GRANT SELECT, INSERT, DELETE ON products TO user1, user2;
GRANT ALL PRIVILEGES ON TABLE employees TO IT_role WITH GRANT OPTION;
```

**REVOKE**
- Remove any already granted access rights from a user. 
Syntax,
```sql
REVOKE [GRANT OPTION FOR] privilege_name
ON object_type object_name
FROM user_or_role_name
[CASCADE | RESTRICT];
```
- `GRANT OPTION FOR` : If specified, revokes only the ability for the user to grant that permission to others, but does not revoke the permission itself.
- Object type Object name : ex: `TABLE employees`, `DATABASE sales`
- CASCADE: Automatically revokes the permission from any other users or roles that the specified user granted it to
- RESTRICT: Prevents the `REVOKE` operation if the user has granted the permission to someone else, requiring the other grants to be revoked first.
Ex:
```sql
REVOKE SELECT, INSERT, UPDATE ON sakila.customer FROM 'manager';
REVOKE ALL PRIVILEGES ON database_name.table_name FROM 'user_name'@'host_name';
REVOKE GRANT OPTION FOR SELECT ON Users FROM 'Amit'@'localhost';
```

Cascade effect,
Revoking the Bob's `Grant Option For` in `cascade` mode.

#### Inference
There may be a combination of data that is more sensitive than the individual items. 
An **inference issue** (or **inference problem/attack**) occurs when a user can combine seemingly non-sensitive or low-security data and metadata to deduce sensitive or high-security information that they are not authorized to access directly.

The information transfer path which allows to access unauthorized data obtained from non-sensitive data is called the "inference channel".
![[Pasted image 20251228165016.png]]

Approaches to handles,
1. Inference detection during database design
	Removes an inference channel by altering the database structure or by changing the access control regime to prevent inference.
	Ex: 
	- Splitting tables and remove data dependencies between them
	- Fine grained RBAC scheme.
2. Inference detection at query time
	Eliminate an inference channel violation during a query or series of queries. If an inference channel is detected, the query is denied or altered

#### Database encryption
Data encryption enhance the database security. 
Encryption can be applied to the entire database, at the record level, at the attribute level, or at the level of the individual field.
Disadvantages of database encryption,
1. Key management
	Authorized users must have access to the decryption key for the data for which they have access. With the authorized users get increased, this can be complex.
2. Inflexibility
	When a database(or a part of it) is encrypted, it becomes more difficult to perform record searching. 
In order to facilitate key management and ensuring flexibility, it would be better to encrypt individual records as blocks, instead of encrypting an entire database.
