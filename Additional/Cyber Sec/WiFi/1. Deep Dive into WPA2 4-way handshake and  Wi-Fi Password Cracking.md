### The 4-way handshake - more detailed version

PSK : Pre-Shared key
	the password you enter to connect to a Wi-Fi.
	Human readable string.
PMK : Pairwise Master Key
	A 256-bit cryptographic key that is derived from the PSK and the network's SSID.
	The PMK is generated on both the client and the access point through a process called a **Key Derivation Function**. 
	PMK is never transmitted over the air. 
	PMK itself is not used for data encryption, instead it acts as a "master" key to create other, temporary keys for a specific session(like PTK).
	Once the PMK is established, a 4-way handshake occurs. 
PTK : Pairwise Transient Key
	A temporary, 512-bit key used to encrypt all unicast data between a client and a wireless AP. 
	It derived independently by both the client and the AP during the 4-way handshake using a key derivation function. 
	It's unique to a specific client-AP connection and is derived for each new connection session. 
	==PTK itself is not transmitted over the air.== 
GTK : Group Temporal Key
	Used to encrypt multicast and boardcast traffic. 
	Unlike the PTK, which is unique for each client and used for one-to-one communication, the GTK shared among all connected clients on the network. 
	GTK is generated by the AP and shared among all the clients during the 3rd stage of the 4-way handshake. 

PTK is unique to each client-AP connection. 
	So the unicast traffic is secured.
GTK is generated by the AP and shared among all connected clients.

##### Workflow,
MSG 1 : (AP -> Client)
	Contains the **ANonce**(AP nonce) and header info (BSS/AP, MAC, etc...)
	ANonce(stands for Authenticator nonce) is the first ingredient for they key derivation. This message is un-encrypted.
MSG 2 : (Client -> AP)
	The client receives the ANonce and generate it's own random number called **Supplicant Nonce(SNonce)**. 
	It then independently calculates the PTK using the PMK, the ANonce, the SNonce and and both Client's and AP's MAC addresses. 
	The client then sends the SNonce and a **Message Integrity Code**(MIC) to the AP. The MIC acts as a signature, proving the client knows the PMK.
	This message is encrypted.
	(This message contains the SNonce and MIC in an **EAPOL frame** that includes a MIC calculated by the client using the PTK(Pairwise transient key)).
MSG 3 : (AP -> Client)
	The AP now having all the necessary nonces and MAC addresses, also independently calculates the PTK.
	It then uses a part of the PTK to encrypt a **Group Temporal Key(GTK)** and sends it along with a new MIC to the client.
MSG 4 : (Client -> AP)
	The client uses the derived PTK to de-crypt the GTK and verifies the MIC. 
	If everything checks out, it sends a final acknowledgment(ACK) to the AP.
	This final message is un-encypted.

Key points,
- ANonce and SNonce are public nonces and travel in clear.
- The PSK is never transmitted.
- The MICs are cryptographic tags computed using the PTK and the PTK itself is derived from the PMK(which depends on the PSK) and the nonces and MAC addresses. 

##### What an offline cracker need to verify a passphrase,
We need, 
- ANonce(form the AP)
- SNonce(from the client)
- AP MAC and Client MAC
- An EAPOL frame that contains a MIC computed using the real PTK(PTK can be captured during a successful handshake).

> [!NOTE] Note
> The MIC you captured from a successful handshake is the key info. 
> Without a valid MIC, step 3,4 are impossible.

#### Even using a rogue AP with a different PSK
If your rogue AP advertise the same SSID but uses a different PSK,
- The rogue AP sends a ANonce. 
- The client responds with SNonce and computes a MIC using the PTK derived from the real PMK. (because the client uses its stored correct PSK and SSID to generate the correct PMK).
- The rogue AP is using a different PSK. So when it tries to compute/check MICs using its own PMK, its computed MIC will not match the client's MIC. The rogue AP will detect MIC mismatch and abort.

==Since the rogue AP terminate the handshake process from 3rd step, it will not emit the MIC at the rd stage of the handshake. But still, if we capture a complete MIC from the 2nd stage, we can crack it offline.==
==Because the MIC is generated from a device which knows the real PSK then have a valid PMK.==

A useful capture = ANonce + SNonce + AP MAC + Client MAC + EAPOL frame containing the MIC(from the client or AP) 
Useless capture = missing or corrupted MIC, missing nonces or an incomplete EAPOL payload.

You can capture the whole 4-way handshake when a client connecting to the real AP.

Then you can crack it using a dictionary attack. 
##### Cracking workflows(after capturing MIC),
- PBKDF2(candidate password+SSID)  -> candidate PMK
- Using ANonce, SNonce, AP MAC, Client MAC and the candidate PMK  -> derive the candidate PTK(via the PRF algorithm)
- Compute the MIC over the captured EAPOL payload using the candidate PTK.
- Compare the computed MIC to the Captured MIC from the real handshake.
	If they match, the candidate passphrase is correct.
	If they do not match, the candidate is wrong.
****
#### Key Derivation chain of WPA2
1. PMK = PBKDF2(password, SSID, 4096, 256 bits)
	Inputs : The human readable password(PSK), SSID, Iteration count(4096 in WPA2)
	Output : 256-bit PMK(long-term key for WPA-PSK)
2. PTK = PRF-X(PMK, "Pairwise key expansion", Min(MACs)|| Max(MACs) || Min(ANonce,SNonce) || Max(ANonce,SNonce))
	The PRF is built from HMAC(Commonly HMAC-SHA1 in WPA2)
	PTK length = 48 bytes(384 bits) for WPA2 and broken into subkeys,
	- KCK(Key Confirmation Key) : First 16 bytes(used to compute/verify MICs)
	- KEK(Key Encryption Key) : Next 16 bytes(used to encrypt key data)
	- TK(Temporal Key) :  last 16 bytes(used for data encryption like CCMP)
3. MIC = MAC(KCK, EAPOL_payload_with_MIC_field_zeroed)
	- The EAPOL frame (Key descriptor and fields) is serialized, the MIC field itself is zeroed when computing the MAC, then the MAC(HMAC with KCK) is produced. 
	- The exact MAC/HMAC algorithm depends on key descriptor version(often HMAC-SHA1 or HMAC-SHA256 variants)
So the MIC is a keyed MAC(Message Authentication Code) over the handshake message, keyed with KCK which itself come from PTK <- PRF(PMK, nonces, MACs)

# Caveats & related attacks (educational)

- **PMKID attack**: a different flavor — in some setups you can extract a PMKID from the AP itself (from certain RSN fields). That produces a hash that can be cracked offline without needing a full, successful 4-way handshake with a client. PMKID attacks are separate and have different requirements; they’re worth studying in your lab as an alternative vector.
- **Rogue AP that _matches_ the PSK:** if the attacker somehow used the _same_ PSK (e.g., attacker already knew it or guessed it), then the rogue AP will complete a valid handshake with the client and you _can_ capture a usable handshake for offline verification (but in that case you already had the PSK or you cracked it somehow).
- **Partial captures:** sometimes network loss/truncation causes some EAPOL fields to be missing; even if you see ANonce and SNonce, if the MIC or relevant EAPOL payload bytes are missing/truncated the offline test will fail.
