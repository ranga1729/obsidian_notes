# 3.1 Black-Box Testing
![[Pasted image 20260531201659.png]]
Testing without having any knowledge of the interior workings of the application. 
Appropriate for all levels of testing.

Characteristics,
- Test conditions, test cases, test data are derived form a test basis including SRS, use cases and user stories.
- Test cases may detect gaps or derivation from the original requirements.
- Coverage is based on the items tested in the test basis. 

Techniques,
1. Equivalence Partitioning(EP)
2. Boundary Value Analysis
3. Decision Table Analysis
4. State Transition Testing
5. Use Case Testing

#### 1. Equivalence Partitioning(EP)
![[Pasted image 20260531202823.png]]
EP divides the input data into groups (partitions) that are expected to be processed by the system in the same way. You assume that if one value in a partition works, all others will too.

Goal: Minimize the number of test cases by selecting only one representative value form each partition. 

Ex: For an age field accepting 18-65, partitions are,
	Invalid(<18)
	Valid(18-65)
	Invalid(>65)
When writing test cases, we don't need to write 10,15 test cases. 
Instead we take one test case from each class and assume if one condition in a partition works, all of the conditions int hat partition will work. If one of the conditions in a partition does not work, it is assumed that none from that class works. 
#### 2. Boundary Value Analysis
![[Pasted image 20260531203722.png]]
testing the edges of the input partitions. Defects are most likely to occur at the boundaries rather than in the center of a range.

Ex: Ex: For an age field accepting 18-65, partitions are,
	Invalid(<18)
	Valid(18-65)
	Invalid(>65)
We write test cases for, 
	17,18,19 - lower boundary
	64, 65, 66 - upper boundary
#### 3. Decision Table Testing
![[Pasted image 20260531204103.png]]
Used for systems where the output depends on complex combinations of multiple input conditions. You create a table representing all possible combinations of conditions and their corresponding actions.
AKA **"Cause-Effect table"**.

Goal: Ensure all logical combinations are covered, especially when "if-then-else" logic is involved.

Ex: A loan approval system where eligibility depends on _Credit Score_, _Income_, and _Existing Debt_.

Steps, 
1. Identify a suitable function or subsystem which reacts according to a combination of inputs or events.
2. Identify all the inputs and create a table with true false values for each condition.
3. Identify outputs according to the decision combinations. 
4. Write test cases addressing each combination.
#### 3. State Transition Testing
![[Pasted image 20260531212149.png]]
Used for systems that move through different states based on events or inputs. You model the system's behavior by mapping states, transitions, and the events that trigger those transitions. 

Goal: Verify that the system reaches the correct state after a specific event and handles invalid transitions correctly.

Ex: An ATM machine's state flow: _Idle_ $\rightarrow$ _Card Inserted_ $\rightarrow$ _PIN Entered_ $\rightarrow$ _Transaction Processed_.

Four basic parts of the state machine model,
1. The state that the software may occupy. (ex: open/closed)
2. The transition from one state to another. (ex: not all transitions are allowed)
3. The event that causes the transition. (ex: closing a file)
4. The action that result from the transition. (ex: an error)

Test conditions are derived from the state graph. 
Each state, transition can be noted as a test condition. 

**What's a State Table ?**
![[Pasted image 20260531213034.png]]
Deriving tests only from a state graph may miss some edge cases/invalid transitions. 
State table is created to include all state and transitions both valid and invalid. 
#### 5. Use Case Testing
Testing the application through the lens of user-defined scenarios (Use Cases). It follows the interaction between the user and the system from start to finish to ensure the business process works.

Goal: Validate the end-to-end functionality as a user would experience it, including both "happy paths" (successful scenarios) and "alternate paths" (errors or edge cases).

Ex: Testing the entire flow of "User places an order" $\rightarrow$ "Adds to cart" $\rightarrow$ "Payment" $\rightarrow$ "Confirmation email received."

**What is a use case ?**
![[Pasted image 20260531214623.png]]
A description of a particular use of the system by an actor (a user of the system).
Each use case describes the interactions the actor has with the system in order to achieve a specific task. 
Each use case must specify any preconditions and postconditions that need to be met for the use case to work successfully. 

# 3.2 White-Box Testing
![[Pasted image 20260531220951.png]]
Tester has internal knowledge of the application's source code, architecture, and design. primary objective is to verify the internal logic, data flow, and control structures of the code rather than just the functional requirements. Can be used at all levels of testing. 

AKA,
- Structural testing
- Glass-box testing
- Clear-box testing 

Characteristics,
1. Test conditions, test cases, test data are derived from a test basis that include the code, software architecture, detailed design.
2. Coverage is measured based on the items tested within a selected structure. (ex: code or interfaces)
3. Specifications are often used as an additional source of information. 

Techniques,
1. Statement testing and coverage
2. Decision testing and coverage

**Test Coverage**
Test coverage is a metric used to measure the extent to which the application's requirements or code have been exercised by the test suite. It is a quantitative indicator of how much of your software has been verified and, conversely, what areas remain untested.

For requirement based coverage(functional testing),
$$
Coverage = \frac{\text{Number of requirements tested}}{\text{Total number of requirements}} \times 100
$$
#### 1. Statement Testing
Statement Testing is a white box testing technique in which test cases are designed to execute each statement of a program at least once.
Through statement coverage, we can identify the statements executed and where the code is not executed because of blockage.

Statement coverage,
$$
Coverage = \frac{\text{Number of stateents executed}}{\text{Total number of statements}} \times 100
$$
Ex: 
```text
READ X
READ Y
IF X>Y
	THEN Z = 0
ENDIF
```

| Test <br>Case | Values of X and Y | No of statements executed | Statement coverage |
| ------------- | ----------------- | ------------------------- | ------------------ |
| Test 01       | X=5, Y=5          | 5                         | 5/5*100 = 100%     |

#### 2. Decision Testing
A white-box testing technique which exercises the decisions in the code and tests the code. 

Types of decisions, 
1. IF statements
2. Loop control statements like DO-WHILE or REPEAT-UNTIL
3. CASE statements

$$
Coverage = \frac{\text{Number of decision outcomes tested}}{\text{Total number of decision outcomes}} \times 100
$$
Ex: 
```text
READ X
READ Y
IF X>Y
	THEN Z = 0
ENDIF
```
Same with statement testing got 100% coverage after executing the code one time. 
But decision can generate outputs based on different values. 

| Test <br>Case | Values of X and Y | No of statements executed | Statement coverage |
| ------------- | ----------------- | ------------------------- | ------------------ |
| Test 01       | X=5, Y=3          | 5                         | 5/5*100 = 100%     |
| Test 02       | X = -2, Y = 8     | 4                         | 4/5*100 = 100      |
This now covers both of the decision outcomes,
- Test 01 - True
- Test 02 - False

##### Value of Statement and Decision Testing
Statement coverage helps to find defects in code. 
When 100% statement coverage is achieved, it ensures that all executable statements in the code have been tested at least once.

But it does not ensure that all decision logic has been tested.

Decision coverage helps to find defect in code.
When 100% decision coverage is achieved, it executes all decision outcomes.

Achieving 100% decision coverage guarantees 100% statement coverage.
But not vice versa.

# 3. Experience Based Test Techniques
Test cases are derived from the tester’s skill and intuition, and their experience with similar applications and technologies.
These techniques can identify issues that other methods can not reveal easily. 

Techniques,
1. Error guessing
2. Exploratory Testing
3. Checklist-based Testing

#### 1. Error Guessing
Anticipate the occurrence of errors, defects, and failures, based on the tester’s knowledge. 
As good testers know where the defects are most likely to lurk, this method heavily depend on the testers skills. 

There are no rules for error guessing. 
Common tricks,
- Division by zero
- Blank input
- Empty files
- wrong data types
#### 2. Exploratory Testing
A hands-on approach in which testers are involved in minimum planning and maximum test execution.
The test design and test execution activities are performed in parallel typically without formally documenting the test conditions, test cases or test scripts.
A key aspect of exploratory testing is learning where tester explores and learns about the software, its use, its strengths and its weaknesses.
Useful when there are no or poor specifications and when time is severely limited.

#### 3. Checklist-based Testing
Testers design, implement, and execute tests to cover test conditions found in a checklist.
Such checklists can be built based on experience, knowledge about what is important for the user, or an understanding of why and how software fails.
