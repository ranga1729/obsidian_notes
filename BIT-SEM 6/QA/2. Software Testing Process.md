# 2.1 The Nature of Test Process
Effective and efficient testing requires test approached that properly planned and carried out, 
- With test designed and implemented to cover the proper areas of the system
- Executed in the right sequence
- With their results reviewed regularly

Testing is a "process" with tasks and activities.
There's no universal test process. Right test process is the one that achieves your test objectives in the most efficient way. 

Factors that influence a particular test process,
1. SDLC model and project methodologies being used. 
2. Test levels and test types required.
3. Product and project risk. (low risk = less formal test process)
4. Business domain
5. Operational constraints(budget, resources, timescales, complexity, ...)
6. Organizational policies and practices
7. Internal and external standards.

# 2.2 Test Activities and Tasks
Key test activities,
1. Test planning
2. Test monitoring & control
3. Test analysis
4. Test design
5. Test implementation
6. Test execution
7. Test completion

#### 1. Test planning
Involves defining objectives of testing. 
Decisions,
- Suitable test technique
- Tasks need to be done
- Test schedule
#### 2. Test monitoring & control
Test monitoring involves,
- checking the status of the testing
- Identify variance from expected plan
- Reporting status
We monitor test against **"exit criteria"**(definition of done).

Test control: Applying a set of corrective actions to get a test project on track when monitoring shows a deviation from what was planned. 
#### 3. Test analysis
Identifies test condition by analyzing the test basis.

> [!NOTE] Test Basis
> The body of knowledge used as the basis for test analysis and design. 
> Ex: 
> - SRS
> - Design and implementation information
> - The code itself
> - Risk analysis reports

> [!NOTE] Test Condition
> An aspect of test basis that is relevant in order to achieve specific test objectives. 

Activities in test analysis,
1. Analyze the test basis relevant to the current test level.
2. Identify defect based on the test basis and test items. 
3. Identify features to be tested.
4. Prioritize test conditions for each feature. 
5. Capture bi-directional traceability between test basis elements and associated test conditions.

Types of defects,
- Ambiguities
- Omissions
- Inaccuracies
- Inconsistencies
- Contradictions
- Superfluous statements

Test techniques,
- black box
- white box
- experience based

what expected to be found when identifying what to test during the test analysis phase,
- Missing requirements
- Contradictory statements between documents
Test analysis help validate if the requirements properly capture stakeholder requirements. 
#### 4. Test Design
Deriving test cases from test conditions.
Address the question "how to test ?"
Test analysis identifies the general areas to test. Test design make these general area specific for components.
Similar to test analysis, test design also can identify defects in the test basis and existing test conditions.

Activities,
1. Design an prioritize test cases.
2. Identify necessary test data.
3. Design test environments. (infrastructure and tools)
4. Capture bi-directional traceability between the test basis, test conditions and test cases and test procedures. 
#### 5. Test Implementation
Prepares the testware needed for test execution based on test analysis and design. 
Test procedures are specified in test implementation. 
Involves setting up the environment as well. 

> [!NOTE] Test Procedures
> A sequence of test cases in execution order, and associated actions that may be required to set up the initial preconditions and wrap-up activities post execution.

Activities,
1. Develop and prioritize test procedures/automated test scripts.
2. Create test suites from test procedures. 
3. Arrange test suites within a test execution schedule. 
4. Build the test environment. 
5. Prepares test data.
6. Verify and update bi-directional traceability between test basis, test conditions, test cases, test procedures and test suites. 

> [!NOTE] Test Suites
> A set of test cases or test procedures to be executed in a specific test cycle. 

> [!NOTE] Test Execution Schedule
> A schedule for the execution of test suites within a test cycle. 
#### 6. Test Execution
Running a test on the component or system under test, producing actual results. 
Test suites assembled in test implementation are executed as the schedule. 

> [!NOTE] Testware
> Work products produced in the test process for use in planning, designing, executing, evaluating and reporting on testing.

Activities,
1. Document all items, test objects, test tools, and other testware.
2. Execute the tests.(Manual or Automated)
3. Compare actual results with expected results.
4. Identify anomalies, likely causes. 
5. Report defects.
6. Log the outcome of test execution(pass, failed, blocked)
7. Verify and update bi-directional traceability between the test basis, test conditions, test cases, test procedures and test results. 
#### 7. Test Completion
Makes test assets available for later use, leaves test environment in a satisfactory condition and communicates the results of testing to relevant stakeholder.
Test completion activities should occur at major milestones and specific milestones should be specified in the test plan. 

Activities,
1. Check if all defects reports are closed, change requests have been entered, product backlog is intact.
2. Creates a test summary report. 
3. Finalize and archive test environment, test data, and infrastructure and testware. 
4. Handover testware to the maintenance team/other project team/stakeholders.
5. Analyze lessons learned from completed tests activities to determine future iterations, releases and projects.
6. Improve test process using the information gathered from the test.

### Test work products
work product: The generic name given for any form of documentation, informal communication or artifacts that is used in testing.
In each phase, we create different work products. 

Ex: 
1. Test planning work product - Test plans
2. Test monitoring and control work products - Test reports
3. Test analysis work products - Test Conditions
4. Test design work products - Test cases
5. Test implementation work products - Test procedures, Test suites, execution schedule.
6. Test execution work products - Status report of each test cases/procedures, defect reports, Documentation about test objects, tools, testware
7. Test completion work products - Test summary reports, learned improvements required, change requests/backlog items, finalize testware.  

# 2.3 Traceability between the test basis and test work products
![[Pasted image 20260531130952.png]]
Traceability: The degree to which a relationship can be established between two or more work products.

Bidirectional traceability in Quality Assurance is the process of mapping and tracking requirements to test cases and, conversely, test cases back to requirements throughout the entire software development lifecycle (SDLC).

Types, 
1. Forward Traceability(Requirement to Test): Ensure that all specified requirements are covered by test cases. 
2. Backward Traceability(Test to Requirements): Ensures that every test case serves a legitimate purpose derived from a requirement.

Ex:
The Traceability Matrix(RTM)

| Requirement ID | Requirement Description | Test Case ID | Test Status |
| -------------- | ----------------------- | ------------ | ----------- |
| REQ-01         | User Login              | TC-101       | Passed      |
| REQ-01         | User Login              | TC-102       | Passed      |
| REQ-02         | Password Reset          | TC-201       | Passed      |

Good traceability support, 
1. Impact analysis of chnages
2. Making tests auditable by being able to measure coverage. 
3. Meeting IT governance criteria
4. Improve the relationship between progress reports and summary reports.
5. Relating technical aspects of testing to terms that stakeholders would understand. (by linking the test cases to requirements)
6. Provide info to assed product quality, capabilities, and progress. 
# 2.4 Software Development and Software Testing
Testing must fit with the SDLC model being used. 

Ex: 
	If time to market is a key factor, then the testing must be rapid. 
	If the documentation is a key outcome, testing must be well documented.

Characteristics of good testing, Regardless of the SDLC model,
1. Every development activity has corresponding test activity. 
2. Each test level has test objectives specific to that level. 
3. The test analysis and design for a given test level must begin during the corresponding development activity.
4. Testers should participate in discussions of refining requirements and design. 
### Sequential Development Models 
#### 1. Waterfall Model
![[Pasted image 20260531133619.png]]
Testing tends to happen at the end of the cycle.
Defects are detected close to the live implementation date.
Difficult to get feedback passed backwards up the waterfall. 
#### 2. The V-model
![[Pasted image 20260531133814.png]]
Every single phase is directly associated with testing phases. 
Provides guidance on how to testing begins as early as possible. 

Types of tests used in V-model,
1. Component/Unit testing: Test software components separately and identify defects.
2. Integration Testing: Test interactions between components.
3. System Testing: Test the system as a whole. 
4. Acceptance Testing: Validation testing with respected user needs, requirements and business process. 

### Iterative Development Models
![[Pasted image 20260531134418.png]]
Tests are carried out in a iterative and incremental environment.

Common issues with iterative models,
1. More regression testing.  
2. Defect outside the scope of the iteration or increment. 
3. Less thorough testing. 

Examples of iterative and incremental development models,
1. Rational unified Process(RUP)
2. Scrum
3. Kanban
4. Spiral(or prototyping)
5. Agile
6. Extreme Programming(XP)

Scrum and XP emphasizes testing throughout the process.
Each iteration(sprint) has a short period of testing. 

Benefits of incremental models,
1. Focus on working software and quality of the code. 
2. Simplicity of design helps testing.
3. The inclusion of testing into the development. 

Challenges, 
1. Time pressure. Less time to think about testing.
2. Regression testing becomes extremely important. 
3. Test design is less formal and subject to changes. 
4. Testers may acts as coachers in testing to both developers and stakeholders. 

# Software Testing Methodologies
### 1. White-box Testing
Tester has internal knowledge of the application's source code, architecture, and design. The primary objective is to verify the internal logic, data flow, and control structures of the code rather than just the functional requirements.

AKA,
- Structural testing
- Glass-box testing
- Clear-box testing 

White-box tests for,
1. Internal security holes
2. Broken/poorly structured paths in the code
3. Input flows
4. Expected outputs
5. Functionality of conditional loops
6. Other statements, objects and functions.

Common metrics covered,
- Statements
- Branch/Decisions
- Paths

Techniques, 
1. Statement coverage: Traverse all statement at least once. 
2. Decision overage: Reports Boolean expression of the code.
3. Branch coverage: Each branch from all decision points are traversed at least once.
4. Condition coverage: Check all conditions.
5. Multiple condition coverage: Check all the possible combinations of the possible outcomes of conditions at least once.
6. Finite state machine coverage: check how many time-specific states are visited.
7. Path coverage: Testing all possible paths from including branches.
### 2. Black-box Testing
Tester evaluates the application's functionality without any knowledge of its internal code, implementation details, or internal paths. Focus is entirely on inputs and outputs. Verify the system is working as expected/software specifications.
AKA **"Behavioral testing"**. 

Characteristics,
- Behavioral focus
- Specification based
- Independence/unbiased(testers don't see the code)

Types, 
1. Functional testing: Test functional requirements.
2. Non-functional testing: Not related to testing of specific functionality, but non-functional requirements such as performance, scalability, usability.
3. Regression testing: Done after code fixes, upgrades or any other system maintenance to check the new code has not affected the existing code
### 3. Gray-box Testing
Tester has partial knowledge of the internal application structure, design, or database, but primarily tests the application from the user's perspective.
A hybrid combining black-box and white-box. 
Focus on identify defects caused by improper structure, data handling, or logic integration, while still validating that the system meets end-user functional requirements.

Characteristics,
- Partial visibility
- Informed testing(Testers may have access to design documents and other resources)

## Another Categorization
#### 1. Functional Testing
Focuses on verifying that the software performs the tasks it was designed to do according to the business requirements. 
Can be performed at all test levels. 

Key focus: Features, UI/UX, API endpoints, business processes
Primary methodology: black-box 

Also check for, 
- Suitability
- Interoperability
- Security
- Accuracy 
- Compliance

Two main perspectives,
1. Requirement based testing
	Uses requirement specifications.
	Requirements are prioritized based on a risk criteria and its used to prioritize the tests.
2. Business process based testing
	Uses knowledge of the business processes.
	Use cases are very useful basis.

Techniques used for functional testing are often,
- Specification based
- Experience based

Special skills or knowledge may required for functional testing.
Ex: medical device software

#### 2. Non-Functional Testing
Evaluates the operational attributes/quality characteristics or non-functional attributes of the system. Test "_how well_ the system performs under various conditions". 
Can be performed at all levels.

Key focus: speed, reliability, scalability, security, usability

Types,
1. Performance testing: speed, response time, stability, reliability, scalability, resource usage
2. Load testing: Measure system behavior under heavy traffic. 
3. Stress testing: verifies stability & reliability under extremely heavy load conditions.
4. Usability testing: Test the user-friendliness.
5. Portability testing: Test the easiness of moving a software component. 
6. Compatibility test: Ensuring the software runs on different platforms. 
7. Security testing: Checking for vulnerabilities and data protection.

Special skills or knowledge may be needed.
Ex: Security testing

#### 3. Change-Related Testing
Performed after code modifications are made to ensure that new changes do not negatively affect existing functionality.

Key focus: Verifying the stability of the system after updates

Factors to be aware of,
1. The change itself
2. Any other affected code by the change

Types,
1. Confirmation testing(re-testing): Specifically executing a test case that previously failed to verify that the reported defect has been fixed.
2. Regression testing: Re-running a suite of existing tests to ensure that previously working features still function correctly after code changes.

Can be done at all levels of testing. 

### Test Levels
**Test levels** represent the different stages in the software development lifecycle (SDLC) where specific types of testing are performed.

Each test levels has,
- Specific test objectives. 
- Test basis. work products used to derive test cases.
- Usual defects and failures looking for at this level. 
- Specific approaches and responsibilities. 
- Test environments.

Test levels, 
1. Unit testing(module testing, components testing)
	Focuses on isolated individual components, modules, or functions. 
	Performed by: developers
	Objectives: To verify that the smallest unit of software works exactly as intended
	Technique: Usually White-box
2. Integration testing
	Components/systems are combined and tested as a group to ensure that the interfaces and interactions between modules work correctly.
	Types,
	1. Component integration
	2. System integration
	Performed by: Developers or testers
	Objective: expose defects in the interaction between integrated units.
	Techniques: Black-box, White-box or Gray-box
3. System Testing
	Entire integrated software application is tested as a whole.
	Performed by: QA/Testing team
	Objectives: validate the complete system against the business/functional/non-functional requirements
	Techniques: Primarily black-box
4. Acceptance testing
	Performed before the software is released to the production environment.
	Performed by: users, clients, stakeholders
	Objective: gain confidence that the system satisfies business needs and is ready for real-world use.
	Technique: Black-box

Types of Acceptance Tests, 
1. User Acceptance Testing(UAT)
	Conducted in a real or simulated operational environment by intended users. 
	Focusing on their needs, requirements and business process.
2. Operational Acceptance Testing(OAT)
	Performed in a (simulated) operational environment by operations or systems administration staff.
	Focusing on operational aspects.
3. Contractual Acceptance Testing
	To verify whether a system satisfies contractual requirements
4. Regulatory Acceptance Testing
	To verify whether a system conforms to relevant laws, policies and regulations.
5. Alpha Testing
	Conducted in the developers test environment.
	By roles outside the development organization
6. Beta Testing
	Performed by actual end-users in their own environment.

# Static vs Dynamic Testing
### Static Testing
Examination of software artifacts such as requirements, design documents, and source code **without executing the program**. 
A preventive process meant to identify defects as early as possible in the software development lifecycle.
Performed early in the SDLC (often during the design and coding phases).

Static Testing techniques,
1. Informal reviews - meeting to review non-tech docs
2. Technical reviews - meeting to discuss the technical aspects
3. Walkthrough - author explains the code/docs to the group and get feedbacks
4. Inspections - to identify defects
5. Static code review - automated tools to scan source code for syntax errors, coding standard violations, or security vulnerabilities

### Dynamic Testing
**Executing the software** in a test environment to observe its behavior and response to various inputs.
Performed during the implementation and testing phases, once an executable build is available.

Techniques,
1. Unite testing
2. Integration testing
3. System testing
4. Functional/non-functional testing


| Feature     | Static Testing           | Dynamic Testing      |
| ----------- | ------------------------ | -------------------- |
| Code        | not executed             | executed             |
| Purpose     | Prevention/verificaton   | Detection/validation |
| Timing      | Early in the SDLC        | Later in the SDLC    |
| Cost to fix | Low                      | high                 |
