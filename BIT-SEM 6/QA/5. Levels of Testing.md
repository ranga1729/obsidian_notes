## 1. Functional Testing
Validates the software system against functional requirements.
Can be done wither,
- Manually
- Automation

Test checks,
- User Interface
- APIs
- Database
- Security
- Client/Server communication

#### 1.1 Component Testing/Unit Testing
Searches for defects in components and verifies the function of it. 
Components are testable separately. 

Goals,
- Reducing risks
- Identifying defects in components
- Validate functional
- Improve the quality of components
- Stopping defects from escaping to higher test levels. 

Mock objects, stubs, drivers used to replace missing software to isolate the component. 
	Stub : The components to be tested
	Driver : A component call the stub to be tested. 

Test basis,
- Detailed design
- Code
- Data model
- Component specifications

Possible failures to identify,
- Incorrect functionality
- Data flow problem
- Incorrect code or logic

#### 1.2 Integration Testing
Software modules are integrated and logically tested as a group.
Main objective: Find issues with how various software modules interact when they are combined.

Levels, 
1. Component integration
	Test interactions between components
	Performed after component testing
	Generally automated
	Responsibility of developers
2. System integration
	Test interactions between systems, and micros services.
	Responsibility of of testers.

Objectives,
- Reducing risk.
- Verifying the functionality/behaviors of interfaces.
- Improve the quality of the interface
- Finding defects
- Preventing defects from escaping to later testing

Test basis,
1. Software and system design
2. Sequence diagrams
3. Interfaces and communication protocols
4. Use cases
5. Architecture at component of system level
6. Workflow
7. External interface definitions

Typical defects, 
- Incorrect data, missing data, incorrect encoding
- Incorrect sequencing or timing of interface calls
- Interface mismatch
- Failures in communication between components
- Unhandled or improperly handled communication failures between components
- Incorrect assumptions about the meaning, units or boundaries of the data being passed between components

#### 1.3 System Testing
Testing the whole system as defined by the scope.
Tests may be based on,
- Risks
- Requirement specifications
- Business process
- Use cases

Objectives of system testing, 
1. Reduce risk
2. Verifying is functional and non-functional behaviors are comply with requirements. 
3. Validating if the system is complete.
4. Improve the quality of the system as a whole. 
5. Finding defects.
6. Preventing defect escaping to production. 

Test basis,
- SRS
- Risk analysis report
- Use cases
- State diagram
- Model of system behavior
- System and user manual
- Epics and user stories

Testing objects,
1. Applications
2. Hardware/software
3. OS
4. System Under Test(SUT)
5. System configuration and configuration data

Typical defects and failures,
1. Incorrect calculations
2. Incorrect control or data flow 
3. Incorrect/Unexpected system functional or non-functional behavior 
4. Failure to carry out end to end tasks. 
5. Failure of the system to work properly in the production environments 
6. Failure of the system to work as described in the system and user manuals

Approaches and responsibilities, 
- Carried out by specialist testers. 
- Testing team has involved with the project since the beginning, so they have a good understanding of the system. 
- System test scenarios are usually end-to-end tests that covers the full system. 
- Architects and product owners usually review these scenarios.

Responsibilities of system testing team, 
- Understanding system flows and create high-level user journey.
- Create detailed end-to-end system cases. 
- Identify and generate any test data required to execute the test cases. 
- Coordinate with Scrum teams to ensure adequate support is available to fix defects

System testing types, 
- Usability testing
- Load testing
- Regression testing
- Recovery testing
- Performance testing

#### 1.4 User Acceptance Testing
Conducted in a real or simulated operational environment by intended users focusing on their needs, requirements and business processes. 

Main purpose: Test if the system fulfill user requirements. 

Types of UATs, 
1. Contract Acceptance Testing(CAT)
2. Regulation Acceptance Testing(RAT)
3. Operational Acceptance Testing(OAT)
4. Alpha and Beta Testing

Test basis, 
1. Business process
2. User/Business requirements
3. Use cases
4. System requirements
5. Risk analysis reports
6. Regulations, legal contracts and standards

Test objects, 
1. System under test(SUT)
2. System configuration data
3. Business process for fully integrated system
4. Recovery systems and hot sites
5. Operational and maintenance processes
6. Forms
7. Reports

Typical defects and failures,
- Mismatch between system workflows and user requirements. 
- Incorrect business rules
- System defiance with contractual or regulatory requirements.

## 2. Non-Functional Testing
Evaluate the compliance of a component or a system with non-functional requirements.
Characteristics,
1. Measurable
2. Ensure the quality attributes are identified correctly.
3. Prioritize requirements. 

Parameters, 
1. Interoperability
2. Performance
3. Scalability
4. Security
5. Loading capacity
6. Stability
7. Reliability

#### 2.1 Interoperability Testing
Ensure that the software can interact with other software components and systems.
This prove that end-to-end functionality between two communicating systems is working.

Types of interoperability testing, 
1. Data type Interoperability Testing 
2. Semantic Interoperability Testing 
3. Physical Interoperability Testing 
4. Protocol Interoperability Testing 
5. Data format Interoperability Testing

Interoperability testing can be particularly significant for, 
1. IoT systems
2. Web services with connectivity to other systems
3. Applications based on systems of systems
4. Commercial off-the-shelf software products

#### 2.2 Performance Tests
Determine the performance of the actual system.
Designed for testing the speed, response time, stability, reliability, scalability, and resource usage of a software application.

Main purpose: identify and eliminate the performance bottlenecks

Ex: 
- Maximum number of users the application can handle. 
- Check CPU and memory usage.
- Verify the response time under low, normal and moderate and heavy load conditions. 

#### 2.3 Scalability Testing
Verify that the system can scale up to its engineering limits.

This determines, 
1. how the application scales with increasing workload. 
2. The user limit for a web application.
3. End user experience under load 
4. Server-side robustness and degradation

Test attributes,
1. Response Time
2. throughput
3. Time(Session time, transaction time, task execution time and etc)
4. Network usage
5. Memory usage
6. Performance measurement with number of users
7. Performance measure under load

#### 2.4 Stress Testing
Evaluate and determine the behavior of a software component under extremely heavy load conditions.
Ensures that the system can perform acceptably under worst-case conditions. 

The recovery mechanism should be invoked if the limit exceeds and system fails.

Tests are targeted to bring out the problems associated with, 
- Memory leak
- Buffer allocation and memory craving

Best way to identify system bottlenecks is to perform stress testing from different locations inside and outside the system. 
- Start with innermost components and progressively move outward. 
- Then test from remote locations far outside the system. •
- After all components are tested beyond their highest capacity, test the full system. 
- Incrementally increase the load until the system fails. 
- Observe the causes and locations of failures.

##### 2.5 Security Testing
designed to verify that the system meets security requirements: 
- confidentiality
- integrity
- availability

Objectives, 
1. Test if the software behaves securely under all conditions.
2. Check is the system leaks data or resources during a failure.
3. Check if interfaces and middleware are secure.

New security threats came up with internet, 
1. Un-authorized access to wireless networks
2. Eavesdropping on transmitting data.
3. DOS/DDOS

Types of security tests, 
1. Verify that only authorized access to systems are permitted. 
2. Prevent illegal reading of files. 
3. Set virus checkers preventing viruses get enter into the system. 

##### 2.6 Load and Stability Testing
Designed to ensure that the system remain stable for a long period under full load. 

When a large number of users introduced to a incompatible system, the system can be,
- Slow down
- Encounters functionality problems
- Fail overs
- Crash

This typically involves exercising system with virtual users and measuring the performance to verify whether the system can support the load. 
Helps to understand load-related issues and identify applications behavior in real-life situations.

##### 2.7 Reliability Testing
Test the ability to remain operational for ling period of time. 
Typically expressed in "Mean Time to Failure(MTTF)". 

Testing process,
- Record the time intervals of successive failures($t_1, t_2, t_3,...t_i$) while system testing. Average of i time intervals = MTTF. 
- Measure the time taken by developers to fix the defects. Average of these measurements are called "Mean Time to Repair"(MTTR). 
- Mean Time Between Failures(MTBF) = MTTF + MTTR

##### 2.7 Regression Testing
After doing changes to the code, this is to verify that no defects has been introduced into the unchanged pat of the system. 

To run the regression test, we run the whole test suite(or a subset of the test suite) again.

##### 2.7 Documentation Testing
Verifying the technical accuracy and readability of the user manuals.
Test levels, 
1. Read test : reviewed for clarity, organization flow and accuracy without executing documented instructions. 
2. Hands-on test : Evaluate their accuracy and usefulness. 
3. Functional test : verify that the system works as it has been documented.

Tests, 
- Verify grammar, terminology, and appropriate graphics.
- Verify glossary and commonly accepted terminology. 
- Verify the indexing of each documentation. 
- Verify no inconsistencies within documentations.
