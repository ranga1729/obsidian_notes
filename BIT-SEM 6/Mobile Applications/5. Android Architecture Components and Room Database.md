#### `ViewModal`
A **ViewModel** is a class designed to store and manage UI-related data in a lifecycle-aware manner. It allows data to survive configuration changes, such as screen rotations or keyboard availability changes.

When a device configuration change occurs (like rotating the screen from portrait to landscape), the hosting Activity or Fragment is destroyed and recreated. If UI data is stored directly within the Activity/Fragment, that data is lost. A `ViewModel` remains in memory during these specific teardowns, allowing the newly created UI instance to immediately rebind to the existing data.
![[Pasted image 20260603224934.png]]

Core purpose,
1. Survive configuration changes
2. Separation of concern
	Activities and Fragments should primarily be responsible for rendering data to the screen and handling user interactions. 
	Moving data acquisition, business logic triggering, and UI state management into a `ViewModel` keeps the UI controllers clean and testable.

#### Repositories
In Android MVVM architecture, a **Repository** is a class that abstracts data access and serves as a **mediator between the ViewModel and your various data sources**. It acts as a clean, unified API for the rest of your app, completely hiding how data is fetched, cached, or persisted.

| **Component**  | **Responsibility**                                                       | **Lifespan**                                              | **Scope**                                           |
| -------------- | ------------------------------------------------------------------------ | --------------------------------------------------------- | --------------------------------------------------- |
| **ViewModel**  | Prepares and maintains state for the UI; handles UI business logic.      | Tied to the lifecycle of the host Activity/Fragment.      | UI-centric (knows _what_ the UI needs).             |
| **Repository** | Manages data operations; abstracts data sources (Local DB, Network API). | Typically singleton or tied to the Application lifecycle. | Data-centric (knows _where_ and _how_ to get data). |

## Room Database
![[Pasted image 20260604003644.png]]

The **Room Persistence Library** is a part of the Android Jetpack Architecture Components. It acts as an **Object-Relational Mapping (ORM)** abstraction layer over the native SQLite database implementation in Android.

While Android natively supports SQLite, writing raw SQLite code requires significant boilerplate, manual data parsing, and lacks compile-time validation. Room eliminates these pain points by allowing you to map Java or Kotlin objects to database tables using annotations.

Room relies on three major components that work together to manage the database lifecycle and operations:
1. The database class - `@Database`
	The main access point for the underlying connection to your application's persisted data.
	It defines the list of entities(tables). 
	It provides instances of Data Access Objects(DAOs)
2. Entities - `@Entity`
	Represent tables within your SQLite database.
	Each instance of an entity class corresponds to a row in the associated database table.
	Fields are mapped directly to table columns.
3. Data Access Objects - `@Dao`
	DAOs are interfaces or abstract classes that define the methods used to interact with the database.
	You write Kotlin/Java function signatures and annotate them with `@Insert`, `@Update`, `@Delete`, or `@Query`.
	Room automatically generates the underlying SQLite implementation code for these functions during compilation.

Workflow,
1. the `ViewModal` requests data from the Repository. 
2. The repository calls the appropriate method on the Room DAO.
3. The DAO executes the transaction against the `SQLite` database. 
4. Room return the result back up the chain to the UI. 

**Create a Room Database**
1. Create public abstract class extending `RoomDatabase`
2. Annotate as `@Database`
3. Declare entities for database schema and set version number
```kotlin
@Database(entities= {Word.class}, version = 1)
public abstract class WordRoomDatabase extends RoomDatabase {
	public abstract WordDao wordDao();
	private static WordRoomDatabase INSTANCE; //singleton instance
}
```
- `entity` defines the DB schema.

## Life-cycle aware Components
![[Pasted image 20260605150020.png]]
In traditional Android development, managing lifecycle states required writing significant amounts of boilerplate code directly inside the `onStart()`, `onStop()`, `onResume()`, and `onPause()` methods of an Activity or Fragment. This approach often leads to poor code organization, bloated controllers, and memory leaks. Lifecycle-aware components solve this by shifting the responsibility from the UI controller to the component itself.

Lifecycle-aware components are architectural classes that perform actions in response to a change in the lifecycle status of another component, such as an `Activity` or a `Fragment`.

Participants,
1. Lifecycle owner - An interface(Activity or Fragment) implemented by classes that have an Android lifecycle.
	It exposes a `getLifecycle()` method, which returns a `Lifecycle` object. This allows any external class to observe its state changes. 
2. Lifecycle Observer - An interface (or standard class pattern via Kotlin Coroutines/Flows) used by components that need to monitor the `LifecycleOwner`'s state changes.
	Developers typically implement `DefaultLifecycleObserver`, which provides callbacks for standard lifecycle events like `onCreate`, `onStart`, `onResume`, etc.

Ex:
- Switch between coarse and fine-grained location updates depending on app visibility
- Stop network connectivity when app is in background
- Pause and resume animated drawables

Ex: To create a lifecycle-aware component, implement `DefaultLifecycleObserver` and override the necessary callbacks.
```kotlin
import androidx.lifecycle.DefaultLifecycleObserver
import androidx.lifecycle.LifecycleOwner

class MyLocationTracker : DefaultLifecycleObserver {
    override fun onStart(owner: LifecycleOwner) {
        // Start location updates when the UI becomes visible
        startTracking()
    }
    override fun onStop(owner: LifecycleOwner) {
        // Stop location updates when the UI is no longer visible
        stopTracking()
    }
    private fun startTracking() { /* ... */ }
    private fun stopTracking() { /* ... */ }
}
```

```kotlin
class MainActivity : AppCompatActivity() {
    private lateinit var locationTracker: MyLocationTracker
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        setContentView(R.layout.activity_main)
        locationTracker = MyLocationTracker()
        // Register the observer
        lifecycle.addObserver(locationTracker)
    }
}
```

#### LiveData
`LiveData` is an observable data holder class that is specifically designed to be lifecycle-aware. It keeps a value and allows this value to be observed. 

**how it operates ?**
The data flow relies on the relationship between a `ViewModel`, `LiveData`, and a `LifecycleOwner` (like an Activity).
1. The holder/observer: The `ViewModel` retains the instance of `LiveData`.
2. The Subscription: The `Activity` or `Fragment` subscribes (observes) the `LiveData` instance, passing its own `LifecycleOwner` context.
3. The update: When data changes within the `LiveData` instance, it checks the lifecycle status of the observer. If the observer is active, the UI updates automatically.

When you pass live data through the layers of your app architecture, from a Room database to your UI, that data must be LiveData in all layers,
- DAO
- ViewModel
- repository

Ex: 
```kotlin
//DAO
@Query("SELECT * FROM word_table")
LiveData<List<Word>> getAllWords();

//Repository
LiveData<List<Word>> mAllWords = m.WordDao.getAllWords(); 

//ViewModel
LiveData<List<Word>> mAllWords = m.Repository.getAllWords();
```

Because `LiveData` monitors the lifecycle of its observers, it automatically removes them when their associated lifecycle is destroyed (`ON_DESTROY`). This eliminates the risk of memory leaks caused by lingering references to UI components that no longer exist.

If a lifecycle object becomes inactive, it gets the latest data when it becomes active again

If an activity or fragment is re-created due to a configuration change such as device rotation, the activity or fragment immediately receives the latest available data.

You can extend a LiveData object using the singleton example for services or a database. 

The LiveData object connects to the system service once, and then any observer that needs the resource can just watch the LiveData object.
