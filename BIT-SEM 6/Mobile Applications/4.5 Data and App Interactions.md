#### What's and Intent ?
[[4.2 App Manifest and Resources]]
Intent is an object used to request an action from another app component via the Android System. 
![[Pasted image 20260603022425.png]]

What's an intent can do ?
1. Start an Activity
	Ex: Clicking Share opens an app that allows you to post a photo
2. Start an Service
	Ex: Initiate downloading a file in the background
3. Deliver Broadcast
	Ex: The system informs everybody that the phone is now charging


Types of Intents,
1. Explicit Intents: Starts a specific Activity
2. Implicit Intent: Asks system to find an Activity that can handle this request

Scenarios we use Intents,
1. **Starting an Activity**
An activity represents a single screen in an app.
- To start a new activity: Pass an intent to `startActivity()`. The intent carries any necessary data. 
- To receive result for an activity when it finished: call `startActivityForResult()`. 
- To receive a new intent as a result of an activity: call `onActivityResult()` callback. 

2. **Starting a service**
A component that performs operations in the background without a user interface.
- Start a service: use `JobScheduler`
- To perform a one-time operation: Pass a `Intent` object to the `startService()`. The intent describes the service to start and carries necessary data. 


3. **Delivering a broadcast**
A broadcast is a message that any app can receive.
Ex: when the device is charging, it broadcast an event. 
- To broadcast an event: pass an `Intent` to `sendBroadcast()` or `sendOrderedBroadcast()`

#### Broadcast Receiver
Broadcast receiver is an app component that receives various broadcast event. 
Receivers get notified by,
1. By the system - when an system event occurs that your app is registered for.
2. By another app - including your own if your app is registered for that custom event. 

Two ways to register an broadcast receiver,
1. Static Receiver : Registered in your `AndroidManifest.xml`, AKA **"Manifest-declared receivers"**
2. Dynamic Receiver : Registered using app or activities `context` in your java/Kotlin files. AKA **"Context-registered receivers"**

Starting from Android 8.0(API Level 26), static receivers can't receiver most of the system broadcasts. 

## Shared Preferences and Saving
`SharedPreferences` is a lightweight, framework-managed persistence APIs used to store small collections of primitive data asynchronously. It operates as a simple Key-Value store, saving data directly to a private XML file allocated within your application's internal storage directory on the device hardware.

Use cases:
- User profile flags (ex: `isLoggedIn = true`)
- Application settings and configurations (ex: toggling Dark Mode, enabling Push Notifications)
- Onboarding tracking state (ex: `hasCompletedTutorial = true`)
- Low-security session tokens or API cache markers

Characteristics,
- Primitive types only : ex: `Boolean`, `Float`, `Int`, `Long`, `String` and `Set<String>`. Can't handle complex custom data objects.
- Sandbox isolation: The resulting XML file is stored securely inside your app's private data sandbox (`data/data/your.package.name/shared_prefs/`). Other applications installed on the system cannot read or write to this file.
- Memory Caching: When you initialize `SharedPreferences`, the Android system loads the entire XML file into an in-memory Map. This makes subsequent read operations nearly instantaneous.

Ex:
Need only one preference file per app. 
1. To create a shared preference, `getSharedPreference()`
```kotlin
val sharedPreference = context.getSharedPreference("UserSession", Context.MODE_PRIVATE)
```
- Context can be your Activity, Fragment, or Application context
- Usually name the preference with your app's name.
- Use only `MODE_PRIVATE` to make it secure.

2. Save Data(Write)
We use the `editor` interface of the shared preference to write data. 
```kotlin
fun saveUserData(Context: context) {
	val sharedPreference = context.getSharedPreference("UserSession", Context.MODE_PRIVATE)
	val editor = sharedPreference.edit()
	
	editor.putString("username", "John Doe")
	editor.putInt("user_age", 28)
	editor.putBoolean("is_premium_user", true)
	
	editor.apply()
}
```
- `editor.apply()` method saves changes to memory immediately and writes to disk in the background. 
- `put` method overwrites data if the key exists.

3. Read Data(Restore)
To read data, access the key directly from the `sharedPreferences` instance. You must supply a fallback value to return if the key is missing from the file.
```kotlin
fun readUserData(context: Context) {
    val sharedPreferences = context.getSharedPreferences("UserSession", Context.MODE_PRIVATE)

    // Reading values (the second argument is the default fallback value)
    val username = sharedPreferences.getString("username", "Guest User")
    val age = sharedPreferences.getInt("user_age", 0)
    val isPremium = sharedPreferences.getBoolean("is_premium_user", false)

    println("Username: $username, Age: $age, Premium: $isPremium")
}
```

4. Clear data
Use `.remove()` to remove a specific key and use `.clear()` to wipe all data.
```kotlin
fun removeUsername(context: Context) {
    val sharedPreferences = context.getSharedPreferences("UserSession", Context.MODE_PRIVATE)
    val editor = sharedPreferences.edit()

    // Removes only the "username" key-value pair
    editor.remove("username")
    
    // Wipes out the entire XML file structure contents 
    editor.clear()
    
    editor.apply()
}
```

## Content Providers
![[content-provider-overview.jpg]]
In addition to Activities, Services, and Broadcast Receivers, Content providers and another fundamental core component in native Android App development. 

Primary purpose,
- Manage access to a central repository of data
- Acting as a standardized, secure abstraction interface that connects data inside one application process with code running in an entirely different application process
- Provides a way to share data with other apps

The core concept behind content providers are **"Inter-Process Communication"**(IPC). 
By default, Android isolates apps inside individual Linux sandboxes. App A cannot look inside the file directory or database of App B.
When App B needs to expose its data securely to other apps—or even split data access internally between its own independent modules it implements a `ContentProvider`.

Ex:
- The contact provider: Access the device's address book
- The media store: Queries system-wide photos, videos and audio tracks
- The Telephony/call-log provider: Reads text message threads and call history

##### How to Design an Implement your own Content Provider
To create a custom Content Provider, you must extend the `ContentProvider` class, implement its CRUD methods, and register it in the `AndroidManifest.xml`.

Ex: using a SQLite database helper
```kotlin
import android.content.ContentProvider
import android.content.ContentValues
import android.content.UriMatcher
import android.database.Cursor
import android.database.sqlite.SQLiteDatabase
import android.net.Uri

class TaskProvider : ContentProvider() {

    companion object {
        const val AUTHORITY = "com.example.app.taskprovider"
        val CONTENT_URI: Uri = Uri.parse("content://$AUTHORITY/tasks")

        private const val TASKS = 1
        private const val TASK_ID = 2
        private val uriMatcher = UriMatcher(UriMatcher.NO_MATCH).apply {
            addURI(AUTHORITY, "tasks", TASKS)
            addURI(AUTHORITY, "tasks/#", TASK_ID) // # matches an integer ID
        }
    }

    private lateinit var database: SQLiteDatabase

    override fun onCreate(): Boolean {
        // In a production app, initialize your Room/SQLite database helper here
        // For simplicity, we open/create an in-memory database
        database = SQLiteDatabase.create(null)
        database.execSQL("CREATE TABLE tasks (_id INTEGER PRIMARY KEY AUTOINCREMENT, title TEXT);")
        return true
    }

    override fun query(
        uri: Uri, projection: Array<String>?, selection: String?,
        selectionArgs: Array<String>?, sortOrder: String?
    ): Cursor? {
        val table = "tasks"
        var finalSelection = selection
        
        if (uriMatcher.match(uri) == TASK_ID) {
            finalSelection = "_id = ${uri.lastPathSegment}"
        }
        
        return database.query(table, projection, finalSelection, selectionArgs, null, null, sortOrder)
    }

    override fun insert(uri: Uri, values: ContentValues?): Uri? {
        if (uriMatcher.match(uri) != TASKS) throw IllegalArgumentException("Unknown URI: $uri")
        val id = database.insert("tasks", null, values)
        return Uri.withAppendedPath(CONTENT_URI, id.toString())
    }

    override fun update(uri: Uri, values: ContentValues?, selection: String?, selectionArgs: Array<String>?): Int {
        return database.update("tasks", values, selection, selectionArgs)
    }

    override fun delete(uri: Uri, selection: String?, selectionArgs: Array<String>?): Int {
        return database.delete("tasks", selection, selectionArgs)
    }

    override fun getType(uri: Uri): String? {
        return when (uriMatcher.match(uri)) {
            TASKS -> "vnd.android.cursor.dir/vnd.$AUTHORITY.tasks"
            TASK_ID -> "vnd.android.cursor.item/vnd.$AUTHORITY.tasks"
            else -> null
        }
    }
}
```

Then you must declare the provider inside the `<application>` tag of your `AndroidManifest.xml` so the Android OS can discover it:
```xml
<provider
    android:name=".TaskProvider"
    android:authorities="com.example.app.taskprovider"
    android:exported="true" />  ```

## 2. CRUD Operations on an Existing Provider via `ContentResolver`

To interact with any Content Provider (your own or an external one), you use the application `Context` to get a `ContentResolver`.

```kotlin
// Target URI pointing to our custom provider
val providerUri = Uri.parse("content://com.example.app.taskprovider/tasks")
```
#### Read (Query)
```kotlin
fun readData(context: Context) {
    val projection = arrayOf("_id", "title")
    val cursor: Cursor? = context.contentResolver.query(
        providerUri, projection, null, null, null
    )

    cursor?.use {
        val titleIndex = it.getColumnIndex("title")
        while (it.moveToNext()) {
            val title = it.getString(titleIndex)
            println("Task: $title")
        }
    }
}
```

fun writeData(context: Context) {

## How It Works: The Content URI

To query a Content Provider, you do not write raw SQL queries targeting a database file. Instead, you address data structures using a specialized directory path string called a **Content URI (Uniform Resource Identifier)**.

A standard Content URI follows this anatomy: `content://com.example.app.provider/orders/23`
- **`content://`** -> The mandatory scheme component identifying this string as an Android Content URI.
- **`com.example.app.provider`** -> The **Authority**. A unique system-wide string string configured in the app's `AndroidManifest.xml` that tells the OS exactly which Content Provider class should receive the request.
- **`/orders`** -> The **Path**. Identifies the specific data table or folder requested inside the app.
- **`/23`** -> The optional **ID**. Isolates a singular exact record row matching that identifier string index.

Ex:
```kotlin
fun fetchDeviceContacts(context: Context) {
    val contentResolver = context.contentResolver
    
    // Target URI for the built-in system Contacts Provider
    val uri = ContactsContract.Contacts.CONTENT_URI 
    
    // Define columns to extract
    val projection = arrayOf(ContactsContract.Contacts.DISPLAY_NAME)

    // Execute the query
    val cursor: Cursor? = contentResolver.query(uri, projection, null, null, null)

    cursor?.use { 
        val nameIndex = it.getColumnIndex(ContactsContract.Contacts.DISPLAY_NAME)
        while (it.moveToNext()) {
            val contactName = it.getString(nameIndex)
            println("Found Contact Name: $contactName")
        }
    }
}
```

## Services
A Service is an application component that can perform long running operations in the background and does not provide a user interface.

Characteristics of services, 
- Starts with an Intent.
- Can stay running when user switch apps. 
- Life cycle must be managed manually. 
- Other apps can also use the service with proper permissions. 
- Runs in the main thread of its hosting process. 

Use cases,
- Network transactions
- Play music
- Perform file I/O
- Interact with a database

Types of services,
1. Started services (Unbound services)
2. Bound services

![[Pasted image 20260603141103.png]]
##### 1. Started Services(Unbound Services)
Initiated by another component like an Activity calling `startService()`.
It does not stop when the component that started it is destroyed. (fire-and-forget)
It runs continuously until it 
- explicitly stops itself (by calling `stopSelf()`) or 
- another component shuts it down (by calling `stopService()`). 
Once stopped, the OS triggers `onDestroy()`, and the service shuts down.

Workflow,
1. The system calls `onCreate()` to initialize the service if it isn't already running. 
2. It intermediately executes `onStartCommand()` to start the background work. 
3. The service moves into an **Active Lifetime** state where it runs indefinitely in the background.
##### 2. Bound Services(Bound Services)
Initiated when a component calls `bindService()`.
Its lifecycle is strictly tied to its clients. 
It ends automatically when **all clients unbind** by calling `unbindService()`. 
When the last client disconnects, the system triggers `onUnbind()`, followed by `onDestroy()`, and the service shuts down.

Workflow,
1. The system calls `onCreate()`.
2. It then invokes `onBind()`, which returns an `IBinder` communication interface token to the client.
3. It enters an **Active Lifetime** where multiple clients can be simultaneously bound to the single service instance.

while an bound service is being running, other component can bind that to themself by calling the `onBind()` method. then the service will return a `IBind` interface to communicate. 
Once all the bounded clients stop using the services, it will automatically get shutdown. 

#### Foreground Services
A Foreground Service is a specific type of service that performs background operations that are highly noticeable to the user.
Because the task is prominent, Android enforces a strict transparency rule: a foreground service **must display a non-dismissible status bar notification** for as long as it is active. This ensures the user is fully aware that the application is consuming system resources (battery, memory, or network) while the app is closed or in the background.

These services gets high priority than normal background services. And they must provide a notification while running. 

Why Foreground services are needed ? 
To preserve battery and device responsiveness, the Android OS aggressively kills standard background services if the application is not actively open on the screen (especially during deep sleep states known as Doze Mode).

If your app needs to guarantee that a task will not be killed when the user switches apps or locks their screen, you must elevate that task to a **Foreground Service**. The OS treats foreground services with nearly the same execution priority as the active app running on the screen, shielding it from the low-memory killer.

Ex:
- Media playback
- Location tracking
- Active data synchronization
- Connected hardware

#### Background services limitations
- Foreground apps can run both foreground and background services. 
- When an app goes into background, the system stops the app's background services.
- The `startService()` method now throws an `IllegalStateException` if an app is targeting API 26.
These limitations don't affect foreground services or bound services.

## Threads
A thread is the smallest unit of execution within a process. 
##### Main Thread
![[1_Osg7maWK3QBXRXbHM1k0ig.jpg]]
AKA **"UI Thread"**.
Starts as the app boots up. 
Main job is to manage UI.
	Draw pixels
	Animate components
	Handle user inputs

![[Pasted image 20260603182548.png]]
Android updates the screen every 16.67 milliseconds(to maintain 60fps refresh rate). 
If you assign a heavy/time-consuming(DB query, file download, network request) task to the main thread, it get freezes, the UI stops updating. 
If the UI stays frozen for 5 seconds, the OS forces and ANR(Application Not Responding) crash. 

##### Worker thread(Background Threads)
Due to that reason, the main thread must be free of heavy tasks to keep a smooth 
UI. All heavy works must be offloaded to **"Worker Threads"**. These threads run concurrently in the background, executing operations without interrupting the Main Thread's rendering loop.

This is why the Android system mainly maintain a main thread an background threads for an app. 

Two rules for android threads,
1. Do not block the UI thread. 
	Complete all work in less than 16ms for each screen
	Run slow non-UI work on a non-UI thread
2. Do not access the Android UI toolkit from outside the UI thread. 
	Do UI work only on the UI thread

#### `AsyncTask`
![[Pasted image 20260603193230.png]]
Manually writing `Threads` in Java/Kotlin can be messier. 
`AsyncTask` was designed as a helper class to abstract away raw threads. It allows you to perform background operations and seamlessly publish the results back to the Main Thread without manually dealing with thread handlers or synchronizations.

An `AsyncTask` is defined by three generic types `AsyncTask<Params, Progress, Results>` and operates through a strict lifecycle,
1. `onPreExecute()` 
	Runs on the Main thread. 
	Used to set up the task (ex: showing a progress bar).
2. `doInBackground(params...)` 
	Automatically move to a worker thread. 
	This is where you write your  heavy code. It can not touch UI.
3. `onProgressUpdate(Progress)` 
	Runs on the main thread. 
	If you call `publishProgress()` inside `doInBackground()`, this method fires to update UI elements like a download percentage tracker.
4. `onPostExecute(Result)`
	Runs on the main thread.
	Receives the final output from `doInBackground()` so you can safely display the data on the screen or dismiss the loading dialog.

##### Why `AsynTask` was Deprecated
`AsyncTask` is completely unaware of the activity life cycle. 
- If an Async Task was running a 30-second download and the user rotated the phone(configuration gets changed), the original `Activity` would be destroyed and re-created. 
- The `AsyncTask` can keep running in the background, holding an invisible reference to the _old, dead_ Activity.
	This caused massive **memory leaks** and resulted in null-pointer crashes when `onPostExecute()` tried to update a UI layout that no longer existed on the screen.

Solution: **`AsyncTaskLoader`**

##### Loaders
**Loaders** are framework components introduced to handle asynchronous, background loading of data into an Activity or Fragment without blocking the main UI thread. 

Loaders are managed by a system component called the `LoaderManager`.

Characteristics,
1. Lifecycle Awareness
	If a user rotates the screen, the Activity is destroyed and recreated, but the loader survives in memory. It automatically reattaches to the new Activity instance and delivers the data without restarting the background query.
2. Background Execution
	Automatically offload data queries (like heavy disk reads) to a worker thread, eliminating the risk of Application Not Responding (ANR) crashes.
3. Data monitoring
	Many loaders (such as `CursorLoader`) automatically monitor the underlying data source. If the data inside a database or content provider changes, the loader automatically fetches the fresh data and updates the UI in real time.

Two types of loaders,
1. `AsyncTaskLoader` - utilizes a background thread (similar to an `AsyncTask`) to load any type of generic data.
2. `CursorLoader` - A specialized subclass of `AsyncTaskLoader` designed specifically for querying a `ContentProvider`. It runs a background query against a target URI and returns an optimized data database wrapper called a `Cursor`.

#### `AsyncTaskLoader`
**`AsyncTaskLoader`** is a specialized loader that performs the exact same job as an `AsyncTask` (moving work to a background thread), but it is **bound to the lifecycle of the Activity or Fragment** hosting it.
