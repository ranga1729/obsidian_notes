#### Gradle Build System
Gradle an advanced, opensource build system utilized as the official build tool for Android application development.
While android studio facilitate write code, it doesn't compile or package the code. Instead Android Studio delegates these compilations, optimizations and packaging to Gradle.

![[Pasted image 20260520115328.png]]
Gradle acts as the coordinator between compilers, source code files, config files and external dependencies to generate the final deployable asset(an APK)/

Steps,
1. **Compilation:** Compile your code(`.kt` or `.java`) and converts the resulting `.class`bytecode into Dalvik Executable(`.dex`) files via the D8/R8 compiler. 
2. **Resource Processing:** Compile app resources(XML layouts, drawables, assets) into a structured binary format. 
3. **Dependency Resolution:** Fetches required remote and local software libraries(JAR or AAR files) declared in the build config files. 
4. **Packaging:** Combine the DEX files, compiles resources, and manifests, then signs the package using the specified debug or release keystroke cryptographic keys via the APK packager to produce the final executable application.

# 4.2 Working with User Interfaces
#### App manifest and resources
![[Pasted image 20260520150931.png]]
The `AndroidManifest.xml` file is a mandatory root-level configuration file required by every android app. 
Before the OS can execute any application component, read app data or grant system access, it parse this XML file to read application boundaries, security requirements and architectural layout.

Core responsibilities of the `AndroidManifest.xml`,
1. App identification & App metadata 
	This file defines global properties such as package names, app icon, user facing labels, and theme configurations. 
2. Declaration of App components
	Every component must be explicitly registered inside the manifest. 
	Four primary component types must be declared here,
	- `<activity>` : UI screens
	- `<service>` : Background processes without UI
	- `<receiver>` : Receivers listen to system-wide signals(ex: low battery)
	- `<provider>` : Content providers use to share structured data between different apps. 
	If a component is invoked at runtime but is missing from the manifest, the system throws an `ActivityNotFoundException` or runtime failure.
3. Permission Management
	Manifest acts as the central security ledger for system and hardware access. It also declares any permission that other apps must have if they want to access content from this app. 
	Ex: `<uses-permission android:name="android.permission.INTERNET" />`
4. Hardware and Software requirements
	Inform Google Play Store and the OS, which devices can run this app. 
	Ex: Declaring `android.hardware.camera.any` with `android:required=true` prevents devices lacking physical camera from installing this app. 

```xml
<?xml version="1.0" encoding="utf-8"?>
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    package="com.example.secureapp">
    <!-- 1. Permissions -->
    <uses-permission android:name="android.permission.INTERNET" />
    <uses-permission android:name="android.permission.ACCESS_FINE_LOCATION" />
    <!-- 2. Hardware Filtering -->
    <uses-feature android:name="android.hardware.camera" android:required="false"/>
    <!-- 3. Global App Configuration -->
    <application
        android:allowBackup="true"
        android:icon="@mipmap/ic_launcher"
        android:label="@string/app_name"
        android:roundIcon="@mipmap/ic_launcher_round"
        android:supportsRtl="true"
        android:theme="@style/Theme.SecureApp">
        <!-- 4. Component Registration & Intent Filters -->
        <activity
            android:name=".MainActivity"
            android:exported="true">
            <intent-filter>
                <action android:name="android.intent.action.MAIN" />
                <category android:name="android.category.LAUNCHER" />
            </intent-filter>
        </activity>
        <activity 
            android:name=".SettingsActivity"
            android:exported="false" />
        <service 
            android:name=".DataSyncService"
            android:exported="false" />
	</application>
</manifest>
```

When registering a component, the name attribute must be specified with the full package designation. 
Ex:
```xml
<manifest...>
	<application...>
		<activity android:name="lk.ucsc.bitapp.MainActivity">
		</activity>
	</application...>
</manifest>
```
If the first character in the name is a period "`.MainActivity`", this refers to the app's namespace itself. 
	Ex: if the app name is "`lk.ucsc.bitapp`" these activity name is resolved to the same destination.
	`<activity android:name=".MainActivity">`
	`<activity android:name="lk.ucsc.bitapp.MainActivity">`

#### Intents
An "Intent" is a (asynchronous)messaging object in Android system emitted to request an action form another app component. 
Ex: 
1. Open a web UL
2. Download a PDF file
3. User navigate to the dashboard
When a user trigger one of these actions, it will emit an Intent Object to the Android System. 

Types of Intents,
1. Explicit Intents 
	Specify the exact target component by its full qualified Java/Kotlin class name. 
	ex: `Intent(this, DetailActivity::class.java)`
	Android OS delivers this message directly to that class.
	Intent filters are completely bypassed during explicit resolution.
2. Implicit Intents
	Do not name a target components. Instead they declare a general action to perform(ex: open a web URL, take a photo, share a text string).
	Android OS parses all available Intent filters across all installed applications on the device to find components that match the request. 

```kotlin
//open a web url
val intent = Intent(Intetn.ACTION_VIEW, Uri.parse("https://google.com"))
startActivity(intent)

//make a phone call
val intent = Intent(Intetn.ACTION_DIAL, Uri.parse("tel:1234567890"))
startActivity(intent)

//send an email
val intent = Intent(Intent.ACTION_SEND).apply {
	type="message/rfc822"
	putExtra(Intent.EXTRA_EMAIL, arrayOf("recipient@example.com"))
	putExtra(Intent.EXTRA_SUBJECT, "Hello from Android")
}
startActivity(intent)
```
#### Intent Filters
An "Intent Filter" is a declarative expression registered inside the `AndroidManifest.xml` file that defines the capabilities of an android component(an Activity, Service, Broadcast or Receiver).

When an Intent Object detected by the OS, If it's an implicit intent, the OS will parses all available Intent filters across all installed applications on the device to find components that match the request. 
If a particular app has a matching Intent filter inside its manifest file, it will opened. 
If more than one app has matching filters, user will get to choose which app to open.

An **Intent Filter** is the receiving component's advertisement to the Android Operating System, specifying exactly which types of implicit Intents it is capable of handling.

Ex: An activity registers to handle PDF files downloaded from HTTPS web links.
```xml
<activity 
    android:name=".PdfViewerActivity"
    android:exported="true"> 
    <!-- Required to allow external system/apps to launch it -->
    
    <intent-filter>
        <!-- 1. Match the view action -->
        <action android:name="android.intent.action.VIEW" />
        
        <!-- 2. Mandatory category for handling implicit intents -->
        <category android:name="android.intent.category.DEFAULT" />
        
        <!-- Allows web browsers to trigger it -->
        <category android:name="android.intent.category.BROWSABLE" /> 
        
        <!-- 3. Restrict data to specific URL schemes and a specific MIME type -->
        <data android:scheme="http" />
        <data android:scheme="https" />
        <data android:mimeType="application/pdf" />
    </intent-filter>
</activity>
```

Parts of an Intent Filter,
Android OS runs a strict filtering algorithm when evaluating an implicit intent. To pass through an intent filter, the incoming intent must match all three criteria defined inside the `<intent-filter>` XML tag. These parts are, 

1. Action - `<action>`
	Declares the generic string representing the task to perform. A filter can list multiple actions, but an incoming intent need to match only one of them. 
	Ex:
	Tell the system that this component can display data to the user.
	`<action android:name="android.intent.action.VIEW">`
	Used for internal inter-app communication.
	`<action android:name="com.example.action.PROCESS_IMAGE">`
2. Category - `<category>`
	Provides additional contextual information about the character or environment of the component handling the Intent.
	For an Activity to receive any **implicit** Intent, its filter **must** include `<category android:name="android.intent.category.DEFAULT" />`. If this category is missing, the OS will automatically exclude the Activity from implicit resolution.
	Other example: `<category android:name="android.intent.category.LAUNCHER"/>`
3. Data - `<data>`
	Specifies the data URI structure and MIME data types that the component accepts.
	This tag can be broken down into granular attributes: `mimeType`, `scheme`, `host`, `port`, and `path`.
	MIME type: Filter by data format(ex: `image/png`, `video/*`, `application/pdf`)
	URI Schemes: Filters by URL protocols(ex: `http`, `https`, `content`, `file`)


When an application fires an implicit intent matching the parameters,
```kotlin
val intent = Intent(Intent.ACTION_VIEW).apply {
    setDataAndType(Uri.parse("https://example.com/report.pdf"), "application/pdf")
}
startActivity(intent)
```
The android OS inspects its registry:
- If your application is the **only** one on the device with a matching filter, `PdfViewerActivity` launches automatically.
- If multiple applications (e.g., Google Drive, Adobe Reader, and your app) all declare matching filters, the OS presents the user with an interactive system dialog (the **App Chooser / Disambiguation Dialog**) allowing them to select their preferred application.

#### Permissions
Because android executes each app inside an isolated sandbox, apps cannot access restricted device hardware(ex: camera, mic), user data(ex: contacts, SMS) or critical system states by default. 
To break out of the sandbox, the app must explicitly request the corresponding permission.

Permissions are in four categories based on the sensitivity,

| Protection level   | Risk to privacy    | System behavior                                                                                                                     | Example                                    |
| ------------------ | ------------------ | ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| Normal             | Low                | Grant automatically by the system. The user cannot revoke these individually.                                                       | Internet, Vibrate                          |
| Dangerous(runtime) | high               | Requires explicit approval from the user via a system dialog while using the app. Can be revoked at any time.                       | Camera, record Audio, Access Fine Location |
| Signature          | system-level       | Granted automatically _only_ if the app requesting it is signed with the same cryptographic certificate as the app that defined it. | Bind Accessibility Services                |
| Special            | High system impact | Requires the user to navigate deep into system settings to manually flip a toggle.                                                  | System Alert Window, Write Settings        |

Every permission the app sues must be declared in the `AndroidManifest.xml`:
```kotlin
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
    package="com.example.secureapp">
    //Normal Permission: Granted automatically at install
    <uses-permission android:name="android.permission.INTERNET" />
    //Dangerous Permissions: Must also be requested at runtime
    <uses-permission android:name="android.permission.CAMERA" />
    <uses-permission android:name="android.permission.ACCESS_FINE_LOCATION" />

    <application ...>
        //App components
    </application>
</manifest>
```
For any dangerous permission, declaring it in the manifest is the first step. Then you must explicitly check and request it via code. 
![[Pasted image 20260520235147.png]]

```kotlin
private val requestCameraPermissionLauncher = registerForActivityResult(
    ActivityResultContracts.RequestPermission()
) { isGranted: Boolean ->
    if (isGranted) {
        // Permission approved: Execute camera-dependent logic
        openCamera()
    } else {
        // Permission denied: Handle the functional degradation gracefully
        showPermissionDeniedExplanation()
    }
}
```

Devs can define new permissions using `<permission>` tag. 
Built-in permissions are listed in `android.Manifest.permission`.

#### Device Compatibility
Device compatibility can be set in `AndroidManifest.xml` using tags. 
These tags acts as filters. When the app is in Play Store, the store parses these tags and compare them against your device specifications. If the device don't meet the criteria, the app is filtered out and made unavailable to download.

1. **`<use-feature>`** : Hardware/Software capability.
Ex: If your app's basic functionality can not run without a accelerometer,
```xml
<manifest>
	<use-feature 
		anroid:name="android.hardware.sensor.compass"
		andoid:required="true"
	/>
</manifest>
```
- `android:required="true"` : Enforces hard filtering. Devices lacking this feature cannot install the app. 
- `android:required="false"` : Soft filtering. The app can be installed without the feature. But the app must verify hardware's existence at runtime via code before calling APIs dependent on it. 

2. **`<uses-sdk>`** : Platform Versioning
Set the compatibility with different versions of the Android Platform(API levels). 
(Modern Gradle build system inject this tag automatically.)
Ex: 
```xml
<uses-sdk
	android:minSdkVersion=20
	android:targetSdkVersion=21
	android:maxSdkVersion=22
/>
```
- `minSdk` : lowest API level required
- `targetSdk` : API level target that the app was tested and validated against
- `maxSdk` : upper bound API limit. Strongly discouraged to use this by Android as apps should naturally remain forward-compatible with newer OS updates.

3. **`<supports-screen>`** : Display configurations
Ex:
```xml
<supports-screens
    android:smallScreens=["true" | "false"]
    android:normalScreens=["true" | "false"]
    android:largeScreens=["true" | "false"]
    android:xlargeScreens=["true" | "false"]
    android:anyDensity=["true" | "false"]
    android:requiresSmallestWidthDp="integer" 
/>
```

4. **`<uses-configuration>`** : Input Mechanisms
Filters based on physical hardware configurations or input devices attached to the unit. 
Ex:
```xml
<uses-configuration
    android:reqFiveWayNav=["true" | "false"]
    android:reqHardKeyboard=["true" | "false"]
    android:reqKeyboardType=["undefined" | "nokeys" | "qwerty" | "twelvekey"]
    android:reqNavigation=["undefined" | "nonav" | "dpad" | "trackball" | "wheel"]
    android:reqTouchScreen=["undefined" | "notouch" | "stylus" | "finger"] />
```

### File Conventions
- Only the `<manifest>` and `<application>` elements are required. They each must occur only once. 
- Elements at the same level generally not ordered. (ex: `<activity>`, `<service>`) But two exceptions exists,
	1. `<activity-alias>` element must follow the `<activity>` element. 
	2. `<application>` element must be the last element inside the `<manifest>` element. 
- All attributes are optional. 
- Except for some attributes of the root `<manifest>` element, all attribute names begin with an `android` prefix.
- Resources are expressed as values in the format of `@[package:]type/name`. Its ok to omit the `package` name if its provided by library dependencies. If the resource is from Android framework, the package name should be "android". 
- When registering a component(Activity, Service,..) inside the `<application>` block, always use short-hand dot notation if the class is from the base application namespace. Use the fully qualified path only when referencing a component located inside an external feature module or a library with a different base package. 
	**Shorthand:** `android:name=".ui.main.MainActivity"`
	**Fully Qualified:** `android:name="com.example.myapp.ui.main.MainActivity"`
- To prevent namespace collisions with the Android Framework, prefix all custom elements with your unique package name. 
	**Correct:** `com.example.myapp.permissions.INTERNAL_DATA`
	**Incorrect:** `android.permission.INTERNAL_DATA`
 - Some attributes have values displayed to user. (ex: `<application android:label="App Name">`). These should be set from resource or themes instead of hard-coded into the manifest file. 
 - Hardcoding user-facing text strings or configuration variables directly inside the manifest is a severe anti-pattern. Everything except technical identifiers must reference standard Android resource directories.
	 **Labels and Title**: use `@string` reference to support internationalization and localization. 
	 **Icons**: Always reference `@mipmap` resource for app icons (to support various screen density calculations) and `@drawable/` for internal component icons.
	 **Themes**:  Always reference `@style` layouts. 
```xml
<application
    android:icon="@mipmap/ic_launcher"
    android:label="@string/app_name"
    android:theme="@style/Theme.CustomApp"
>
```

Recommended order of elements,
1. **`<manifest>`** (Root tag with namespace definitions and package name)
2. **`<uses-permission>`** / **`<uses-permission-sdk-23>`** (System access requests)
3. **`<permission>`** / **`<permission-group>`** (Custom security boundary declarations)
4. **`<uses-feature>`** (Hardware and software compatibility filters)
5. **`<supports-screens>`** / **`<compatible-screens>`** (Screen configuration controls)
6. **`<queries>`** (Package visibility declarations for Android 11+)
7. **`<application>`** (Global configuration wrapper)
    - `<meta-data>`
    - `<activity>` / `<activity-alias>`
    - `<service>`
    - `<receiver>`
    - `<provider>`
### Providing Alternative Resources
In Android development, the `res/`(Resources) folders a structured repository designed to isolate non-code assets such as XML layouts, UI strings, images, and color palettes from your code. 
#### Grouping
The android build system defines how files must be grouped inside the root `res/` directory. We can not create arbitrary subfolders. 
Files must be categorized into predefined, flat resource type subdirectories,

| Directory Name | Valid File Types     | Primary Purpose & Content                                                                            |
| -------------- | -------------------- | ---------------------------------------------------------------------------------------------------- |
| `anim/`        | XML                  | Property, Tween or frame-by-frame animations.                                                        |
| `color/`       | XML                  | state-lists of colors that change based on view state (e.g., pressed, disabled).                     |
| `drawables/`   | Vector XML, PNG, JPG | Graphic assets, bitmaps, shapes, and layer-lists used for backgrounds and icons.                     |
| `layputs/`     | XML                  | Defines the visual user interface structural architecture of screens and components.                 |
| `menu/`        | XML                  | Defines application menus (e.g., Options menu, Context menu, Navigation Drawer items).               |
| `mipmap/`      | XML, PNG             | Reserved explicitly for application launcher icons to calculate density scaling independently.       |
| `navigation/`  | XML                  | Contains Jetpack Navigation component graphs mapping app destinations and arguments.                 |
| `values/`      | XML                  | Houses arrays, dimensions (`dimens.xml`), strings (`strings.xml`), and global themes (`themes.xml`). |
#### Providing Alternative Resources via configuration qualifiers
Android inherently adapts to varying device dynamics at runtime.
To serve different assets based on the device state, you append **Configuration Qualifiers** to the default directory names using a hyphen (`-`) separator.

Qualifier Appendix Syntax,
`[resource_type]-[qualifier1]-[qualifier2]`

Ex:
- Default fallback: `layout/` (loaded if not specific matches apply)
- Alternative Option: `layout-land` (Loaded only when the device is on landscape mode)

Common qualifiers,
1. **Language and Region (Locale):** * `values/strings.xml` (Default English)
    - `values-es/strings.xml` (Spanish)
    - `values-fr-rCA/strings.xml` (French Canadian)
2. **Screen Smallest Width (`sw<N>dp`):** Defines the minimum width a display must have. Excellent for splitting phone and tablet designs.
    - `layout/` (Phones)
    - `layout-sw600dp/` (7-inch tablets)
    - `layout-sw720dp/` (10-inch tablets)
3. **Screen Orientation:**
    - `layout-port/` (Portrait orientation)
    - `layout-land/` (Landscape orientation)
4. **Screen Pixel Density (DPI):** Serves scaled bitmap images to prevent pixelation or memory bloat.
    - `drawable-mdpi/` (Medium density ~160dpi baseline)
    - `drawable-hdpi/` (~240dpi)
    - `drawable-xhdpi/` (~320dpi)
    - `drawable-xxhdpi/` (~480dpi)
5. **Night Mode (Dark Theme):**
    - `values/themes.xml` (Light theme baseline)
    - `values-night/themes.xml` (Dark theme values)
6. **Platform API Level (`v<N>`):**
    - `values-v31/` (Applies specific styling rules only to devices running Android 12 / API 31 and above)
### Activities and Fragments
![[Pasted image 20260526125013.png]]
Activities and Fragments are the core foundational blocks used to build a user interface(UI) and manage user interaction flows. 

**Activity(The Window):** 
Represents a single, independent screen with a user interface.
Acts as the absolute entry point for user interactions and serves as the windows container that hosts your UI elements. 

**Fragment(The Modular Pane)**
Represents a modular, reusable piece of a user interface that lives strictly inside a host activity. Can not exist independently, Its behavior and lifecycle are directly dependent on the Activity hosting it. 

**How to Add a new Activity ?**
Steps,
1. Create the user interface layout(`activity_detail.xml`)
Create a new XML file inside your `res/layout` directory. This defines the visual structure of your new screen.
```xml
<?xml version="1.0" encoding="utf-8"?>
<LinearLayout xmlns:android="http://schemas.android.com/apk/res/android"
    android:layout_width="match_match"
    android:layout_height="match_parent"
    android:orientation="vertical"
    android:gravity="center"
    android:padding="16dp"
>
    <TextView
        android:id="@+id/titleTextView"
        android:layout_width="wrap_content"
        android:layout_height="wrap_content"
        android:text="Welcome to the Detail Activity!"
        android:textSize="24sp"
        android:textStyle="bold" 
    />
</LinearLayout>
```
2. Create the Activity Class(`DetailActivity.kt`)
Create a corresponding Kotlin class that extends `AppCompatActivity`. This class handles the initialization logic and lifecycle of the screen.
```kotlin
// com/example/myapp/DetailActivity.kt
package com.example.myapp
import android.os.Bundle
import androidx.appcompat.app.AppCompatActivity

class DetailActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
	    super.onCreate(savedInstanceState)
	    // Inflate and bind the XML layout created in Step 1 to this Activity
	    setContentView(R.layout.activity_detail)
    }
}
```
3. Register the Activity in the manifest(`AndroidManifest.xml`)
The Android OS can not launch an Activity unless it is declared in the manifest file.
```xml
<manifest xmlns:android="http://schemas.android.com/apk/res/android" package="com.example.myapp">
    <application
        android:allowBackup="true"
        android:icon="@mipmap/ic_launcher"
        android:label="@string/app_name"
        android:theme="@style/Theme.AppCompat"
    >
        <activity
            android:name=".MainActivity"
            android:exported="true">
            <intent-filter>
                <action android:name="android.intent.action.MAIN" />
                <category android:name="android.category.LAUNCHER" />
            </intent-filter>
        </activity>

        <activity
            android:name=".DetailActivity"
            android:exported="false"
            android:label="Detail Screen" 
        />
    </application>
</manifest>
```
4. Launch the New Activity from your main screen
To navigate from your existing screen (e.g., `MainActivity`) to your new `DetailActivity`, create an explicit **Intent** and execute it using `startActivity()`.
```kotlin
// Inside MainActivity.kt (e.g., inside a button click listener)
fun navigateToDetail() {
    // Construct an explicit Intent pointing directly to DetailActivity
    val intent = Intent(this, DetailActivity::class.java)
    // Request the OS to launch the target Activity
    startActivity(intent)
}
```

### Activity Lifecycle
![[59d40f71d715436_960.jpg]]
Activities are managed as activity stacks. 
When a new activity is started, it is usually placed on the top of the current stack and becomes the running activity, the previous activity always remain below in the stack, and will not come to the foreground again until the new activity exists. 
![[Pasted image 20260526141111.png]]

States of an activity,
- Activity is in the **foreground**, it is active and running. User is interacting with it. Highest position of the activity stack. 
- Activity has **lost focus** due to an non-full-sized or transparent activity has focus on top of the activity. The activity is still alive, visible to the user and maintain the state. 
- Activity is **completely obscured by another activity**. Its stopped or hidden. No longer visible to the user but still maintain the state. 
- The system **drop** the activity from memory. Its destroyed. 

![[Pasted image 20260526150204.png]]
These above host activity transitions through these foundational sequential hooks,
1. `onCreate()` : Triggered when the system first create the activity. Initializes the core logic, setup view binding, inflate the base XML layout using `setContentView()`.
2. `onStart()` : Triggered when the activity visible to the user on screen.
3. `onPause()` : Triggered when a minor event de-focus the screen. The activity is partially obscured but visible. 
4. `onResume()` : Triggered when the activity becomes to the foreground again. User can interact with it again.
5. `onStop()` : Triggered when the activity is no longer visible to the user.(ex: new screen has launched over it or user hit the home button). We can release heavy resources here. 
6. `onDestroy()` : The final callback before the process is completely destroyed by the system or finish by code execution. 

#### Three Key Loops
![[Pasted image 20260526150625.png]]
Refers to the nested lifecycle an activity goes through. 
1. **The Entire Lifetime**
	Duration: From `onCreate()` to `onDestroy()`
	Purpose: The total lifespan of the activity. Setup "global" state in `onCreate()` and release all remaining resources in `onDestroy()`.
2. **The Visible Lifetime**
	Duration: From `onStart()` to `onStop()`
	Purpose: The time the user can see the Activity on-screen. Maintain resources that are needed to display the app to the user such as registering `BroadcastReceivers`.
3. **The Foreground Lifetime**
	Duration: From `onResume()` to `onPause()`
	Purpose: The time the Activity is at the top of the screen and actively has user input focus.

### View
View is the building block of UI components. It occupies a rectangular area on the screen.
Its entirely responsible for drawing itself and handling user interaction events like clicks, touches and key presses.

Every visual elements whether its a piece of 
- Display text(`TextView`) or a  Input field(`EditText`)
- Clickable button(`Button`), menu, other controls
- Scrollable (`ScrollView`, `RecyclerView`)
- An image(`ImageView`) 
- Group views (`ConstraintLayout` and `LinearLayout`)
is a direct subclass of the base `View` class. (`class.view.View`).

> [!NOTE] ViewGroups

Attributes,
1. `layout_width`, `layout_height`: Spatial constraint of the view's rectangular bounding box. 
	1. `match_parent`
	2. `wrap_content`
2. `id` : Unique Id

4. `visibility` : Three values

	2. invisible - Occupies the space but hidden
	3. gone - Occupies 0 space and completely hidden
5. `layout_margin` : Set margin
6. `padding` : set padding

```xml
	android:background="#F5F5F5" 
	android:padding="16dp" 
	android:layout_marginTop="8dp" 
	android:visibility="visible"
/>
```

> [!NOTE] `android:id="@+id/submitButton"`
> Assigns a unique structural integer identifier to the View node within the compiled `R.java` class. This allows you to reference and manipulate the specific View inside your Kotlin or Java code.
> The `+` symbol instructs the resource compiler to generate a brand new resource ID tracking reference

How to create a View in Kotlin code ?
To instantiate a View directly in Kotlin code rather than XML, you must initialize the specific View class by passing it an operating system **`Context`**. An Activity is a direct subclass of `Context`, so when writing code inside an Activity, you can pass **`this`** as the context parameter.

Ex:
```kotlin
// com/example/myapp/DetailActivity.kt
package com.example.myapp
import android.graphics.Color
import android.os.Bundle
import android.view.Gravity
import android.view.View
import android.widget.LinearLayout
import android.widget.TextView
import androidx.appcompat.app.AppCompatActivity

class DetailActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)

        // 1. Instantiate the ViewGroup container (LinearLayout)
        val rootLayout = LinearLayout(this).apply {
            orientation = LinearLayout.VERTICAL
            gravity = Gravity.CENTER
            setBackgroundColor(Color.parseColor("#F5F5F5")) // Light grey background
        }
        // 2. Instantiate the Atomic View (TextView)
        val titleTextView = TextView(this).apply {
            id = View.generateViewId() // Generate a unique ID programmatically
            text = "Welcome to the Programmatic Detail Activity!"
            textSize = 24f // Sets font size in SP (Scalable Pixels)
            setTextColor(Color.parseColor("#212121")) // Dark charcoal text
            textAlignment = View.TEXT_ALIGNMENT_CENTER  
            // Set padding inside the TextView (converting raw pixels to DP requires resources)
            val paddingInPx = (16 * resources.displayMetrics.density).toInt()
            setPadding(paddingInPx, paddingInPx, paddingInPx, paddingInPx)
        }
        // 3. Define Layout Parameters for the TextView
        // This instructs the parent LinearLayout how to measure and place this child View
        val textLayoutParams = LinearLayout.LayoutParams(
            LinearLayout.LayoutParams.MATCH_PARENT, // Width attribute
            LinearLayout.LayoutParams.WRAP_CONTENT  // Height attribute
        ).apply {
            // Set margins outside the TextView boundary
            val marginInPx = (8 * resources.displayMetrics.density).toInt()
            setMargins(marginInPx, marginInPx, marginInPx, marginInPx)
        }
        // 4. Inject the TextView into the LinearLayout container with its layout rules
        rootLayout.addView(titleTextView, textLayoutParams)
        // 5. Render the programmatic rootLayout directly onto the screen window surface
        setContentView(rootLayout)
    }
}
```

### Context
Context is an interface to global information about an application environment. 
Whenever your code needs to perform an action that goes beyond pure computation (like math or manipulating strings) and requires interacting with the outside world, it will require a `Context` instance.

Context is responsible for three primary operations, 
1. Resource and Asset Access
	Ex: `getString(R.string.app_name)`
2. Inter-component Communication
3. System Service and Storage Inspection

Not all context instances are identical.
Context types, 
1. Context Wrapper : A proxy class that delegates all of its framework calls to a base, underlying context. It allows the Android system to modify behavior without altering the original context. 
2. Activity Context : A direct subclass of `ContextWrapper`. It is strictly bound to the **lifecycle of that specific screen**. It contains configuration information regarding the current window, user interface themes, and display metrics.
3. Application Context : An isolated instance bound to the **lifecycle of the entire application process**. It is obtained by calling `applicationContext` inside an activity.
Ex:
```kotlin
class MyBackgroundManager private constructor(context: Context) {
	private val appContext = context.applicationContext
}
```

### ViewGroup and View Hierarchy
A ViewGroup is a specialized subclass of `View` that acts as an invincible container. Its primary responsibility is to hold, position, and manage other child Views. 

The **"View Hierarchy"** is the resulting tree structure generated by nesting multiple Views inside `ViewGroups`. When an Activity renders a screen, it starts at the top node (the Root) and travels down the branch nodes to measure and draw every element.
```text
[Root ViewGroup] (e.g., LinearLayout) 
	├── [Child View] (e.g., TextView) 
	├── [Child View] (e.g., ImageView) 
	└── [Nested ViewGroup] (e.g., FrameLayout) 
		├── [Sub-Child View] (e.g., Button) 
		└── [Sub-Child View] (e.g., Button)
```

`ViewGroup` contains child `Views`. 

### Layouts
![[Pasted image 20260527005731.png]]
`Layouts` are specific types of `Viewgroups`. 
It contain child `Views`. 

Common layouts,
1. `LinearLayout`
	arrange children in a single direction, horizontal or vertical using `android:orientation` attribute. 
2. `ConstraintLayout`
	Position views relative to other sibling views or the parent container using flexible anchor point. 
3. `FrameLayout`
	Acts as a stack or a placeholder block. It blocks out an area on the screen to display a single item. If you add multiple child views to a `FrameLayout`, they will stack directly on top of each other like a deck of cards, pinned to the top-left corner by default.
4. `RelativeLayout` - legacy
	Positions child elements relative to each other (e.g., "place this button below that text view") or relative to the parent edges. Entirely replaced by `ConstraintLayout`.
