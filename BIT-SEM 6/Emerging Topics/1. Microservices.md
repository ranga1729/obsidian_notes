## Microservices Architecture
The foundation of microservice architecture(MSA) is about developing a single application as a suite of fine-grained and independent services that are running in its own process, developed and deployed independently. 

![[Pasted image 20260516144126.png]]

Common misconceptions in MSA,
- Increased line of codes
- Required team size is increased
- MSA is web services re-branded in a new form

Design principles used in MSA,
1. Single Responsibility Principle(SPR) 
2. Service boundaries must align with business capabilities. 
3. Align the microservices design with agile/independent development and deployment.
4. Service design must depend on the scope of the service but not to make the size smaller. 
5. One service should have very few operations/functionalities and a simple message format.
6. Start with relatively broad service boundaries and refactor to smaller one(based on the business requirements) as time goes on. 

### Messaging on Microservices
In monolithic architecture, this was handled via,
- Function calls
- SOA/web services : SOAP(Simple Object Access Protocol) and WebSocket with HTTP, JMS(Java Message Service) etc. 
- Webservices with several dozen of operations and complex message schemas. 

In a microservices architecture, services are decoupled and isolated. Because they do not share a common database or run in the same process space, they cannot communicate via local method calls. 
**Messaging** is a pattern where services communicate by sending packets of data called messages.

Message types, 
1. Synchronous Messaging
Client expects a timely response from the service and waits till it gets it. 
Used in point-to-point communication. 
Protocols used: REST, Thrift(lightweight, cross-platform Remote Procedure Call-RPC framework), gRPC(Google Remote Procedure Call)

2. Asynchronous Messaging
Client doesn't expect a response immediately, or not accepts a response at all. 
Communication is mediated by and intermediary infrastructure component.
Protocols used: 
	AMQP(Advanced Message Queueing Protocol) - Open binary application-layer protocol designed for message-oriented middleware. 
	STOMP(Simple Text Messaging Protocol) - Lightweight, text-based messaging protocol that allows to communicate with message brokers asynchronously.
	MQTT(MQ Telemetry Transport) - Lightweight publish-subscribe messaging protocol designed for resource constrained devices and unreliable networks. 
Message Formats:
	JSON, XML, Thrift, ProtoBuf(Protocol Buffer), Avro
Service contracts:
	Swagger, RAML, Thrift IDL

### Integrating Microservices(Inter-service communication)
Messaging typically follows one of two foundational communications model,
1. **Point-to-Point(Queue)**
Services talk directly to each other over the network using synchronous protocols like HTTP/REST or gRPC. No intermediary infrastructure component handling the message routing. 
![[Pasted image 20260522110007.png]]
Best for: Internal, low-latency, read-heavy operations.
Trade offs: High temporal coupling. If service B is down, service A(the one who invoked B) directly affected. Can cascade the failures across your system. 

2. API-Gateway style
Primarily an External-to-Internal communication pattern rather than a pure inter-service communication pattern. The gateway accepts all incoming requests and route the request to the appropriate downstream microservice.
![[Pasted image 20260522110810.png]]
Trade offs: API gateway can become a single point of failure(SPOF).

3. Message Broker Style(Asynchronous Messaging) 
Asynchronous, mediated communication model designed to completely decouple internal microservices.
Services do not know the network locations or even the existence of other services. Instead they produce events or commands to a centralized middleware platform, a **"Message Broker"**(like RabbitMQ) or an **"Event Streaming Platform"**(like Apache Kafka). Downstream services subscribe to these channels and process payloads at their own pace. 
![[Pasted image 20260522112802.png]]
Best used for: State updates, long-running business processes, background side-effects(ex: processing an order, sending emails, generating reports)
### Data Management
Monolithic Applications use a centralized database. 
All components can perform cross-table JOIN operations. Data integrity is guaranteed by ACID transactions enforced by the DB engine. 
![[Pasted image 20260522113740.png]]

In microservices, the golden rule is **"Database-per-service"**.
![[Pasted image 20260522114158.png]]
Each microservice must own its own data. No other service is allowed to access that database directly. 

Why DB-per-service ? 
- To ensure independent schema evolvements. If two services share the same DB, a schema change required by one service can break the functionalities of the other service.
- Polyglot persistent : Different services have different data needs. (ex: customer service needs a relational DB while recommendation service needs a Graph DB).

**How to access data across services:**
If an operation need multiple database updates in a single transaction, the database of other services should be updated through its service API only. 

Design patterns used:
1. API Composition(Aggregator)
	A specific service queries each microservice sequentially or in parallel via their APIs. 
	Then it grabs individual responses, join data together in memory before sending to the user. 
	Pros: Simple
	Cons: High network overhead, cascading latency(if one service is slows, whole operations slows down)
2. CQRS(Command Query Responsibility Segregation)
	You separate write model(Commands) and the read model(Queries).
	Whenever data changes in the write-optimized service(ex: address update in customer service), they emit an event over a message broker. 
	A dedicated Read service listen to these events and maintain a denormalized database specifically optimized for fast, read-heavy user queries.
	Pros: highly scalable, allows lightning fasts complex queries
	Cons: Highly complex, the read database is eventually consistent.
### Decentralized Governance
In monolithic architecture, development is managed through centralized governance. A single authority decides the tech stack, programming language, DB design, versioning, deployments that every team must follow. 

In MSA, decentralize governance let independent, cross-functional engineering teams building services. A team owns a specific microservice and has the autonomy to choose tools, technologies best suite for the business problem. And the team is responsible for runtime health, performance, and monitoring of their service in production. 

Common aspects such as SLA(Service Level Agreements), throttling, monitoring security requirements and service discovery may be implemented at API-Gateway level. 

### Service Discovery and Service Registry
Service Registry : A highly available database containing the network locations(IP addresses and ports) of all active service instances. 
Service Discovery : The mechanism used by a calling service to lookup that data at runtime and route traffic traffic to a healthy instance. 

**Service Registry**
Before a service can be discovered, its instance must be recorded in the registry. Two primary architectural patterns to this,
1. **Self-Registration Pattern**
	The service instance itself responsible for its lifecycle management. 
	Upon startup, the instance sends an HTTP or TCP request to the Service Registry containing its IP, port, and health check endpoint. It then emits periodic heartbeats to prove it is still alive. Upon a graceful shutdown, it explicitly fires a deregistration request.
	Ex: Netflix Eureka
2. **Third-Party Registration Pattern**
	An external infrastructural component (often called a _Registrar_ or the platform's control plane) detects when an instance boots up or terminates. It automatically handles the entry management on behalf of the container.
	Ex: Kubernetes. When a Pod is created, the Kubernetes API server automatically registers its IP endpoint to the internal Service object abstraction.

**Service Discovery**
Once the data is sitting in the registry, a calling service need to access it to resolve a logical name(ex: inventory-service) into a concrete IP block.

Patterns,
1. **Client-Side Service Discovery**
	Calling service(Client) takes the direct responsibility to find the destination of the callee service by contacting the service registry. 
	![[Pasted image 20260522142746.png]]
	Service A want to send a request to the service B.
	Service A contact the Service Registry and get the valid IPs of the service B. 
	Then service A makes the request to the Service B. 
	(Service A might cache IP addresses locally and runs a client-side load balancing algorithm like round-robin or random selection to pick one IP for the service B.)
Pros: fewer network hops, the client can implement intelligent routing rules. 
Cons: tight coupling between services and the registry. Every service must aware of the service registry. 

2. Server-Side Service Discovery
	Abstract the discovery logic into the network infrastructure layer(a load balancer).
	![[Pasted image 20260522144516.png]]
	Service A want to send a request to the service B.
	Service A contact the load balancer and get the valid IPs of the service B.
	Then the load balancer forward the request to the service B. 
Pros: simple and clean code in services, services don't need to be aware of the service registry.
Cons: extra network hop, load balance becomes a single point of failure
### Microservices Deployment
Requirements,
- Deploy/un-deploy independently of other microservices. 
- Able to scale independently. 
- One service failure should not affect to others. 

Modern MSA requires Service-per-Container. You package each individual microservice, its specific runtime environment, dependencies, configurations into an isolated file system image using Docker. Scaling is done via changing the number of instances. 

![[Pasted image 20260522180708.png]]
Container Orchestration platforms(Kubernetes) extend Docker's capabilities by allowing to.
- manage a cluster Linux container as a single system
- Running docker container across multiple hosts
- Offering co-location of containers
- service discovery and replication control

### Virtual Machine vs. Docker
![[Pasted image 20260522175712.png]]
Virtual Machine:
	Abstract the physical hardware.
	Sit on top of Hypervisor
	Each VM contains a Guest OS. 
	Provides hardware level isolation.
Docker: 
	Abstract the OS. 
	sit on top of the host OS kernel. 
	Container share the Host OS kernel and isolate workloads using native Linux kernel primitives.
	Provides process level isolation. 
### Security with Microservice
In MSA, zero-trust policy is followed. You must explicitly authenticate and authorize every single request whether it comes from an external user or an internal service. And security component implemented at each microservice’s level that uses a central user repository/store
![[Pasted image 20260522185353.png]]
And MSA often leverage API-security standards such as OAuth2 and OpenID connect. 

**OAuth2**
	The client authenticates with authorization server and get an opaque token which is known as "Access Token".
	Access Token has zero information about the user/client but a reference to the user info that can only be retrieved by the Authorization server. 
	AKA **"by-reference token"**.
**OpenID Connect**
	Similar to OAuth2 but issues an Id token which includes user information. 
	Implement with a JWT and that it signed by authorization server. 
	JWT is AKA **"by-value token"**. 
### Design for Failures
MSA should be fault tolerant, be able to recover when possible.
Error handling patterns used,
1. Circuit Breaker
2. Timeout
3. Bulkhead

**Circuit Breaker**
	Prevents an application from repeatedly trying to execute an operation that is highly likely to fail, saving precious resources and giving the failing downstream service time to recover.
	![[Pasted image 20260522201543.png]]
	Circuit breaker monitors all of outcome calls.
	If the failure rate stays below a certain threshold, this remains "closed".
	If the failure rate crosses the threshold, it enters the open state and no network call will be sent to the failing service. Instead the circuit breaker will call a fallback method or cached data. This insulate the downstream service from the traffic while it recovers. 
	After a configurable sleep window expires(ex: 30 seconds), the breaker transitions to Half-"Open". It accepts limited number of trial requests. If those trial requests fail, the breaker assume the service is still broken and flip back to "Open", if not, transit to "Closed".
**Timeout**
	Sets a strict maximum limit on how long a calling service will wait for a response from a downstream dependency before aborting the request.
**Bulkhead**
	If all outgoing service requests share a single global thread pool inside an application runtime, one misbehaving dependency can consume 100% of those threads. This leaves zero processing capacity for healthy, completely unrelated parts of the system.
	Isolate resources by allocating specific, independent thread pools or execution queues to specific downstream dependencies or business domains.
	![[Pasted image 20260522201946.png]]

### Orchestrating Microservice
In MSA, business transactions often span across multiple services.
	Ex: processing a single e-commerce checkout requires talking to the _Order Service_, _Payment Service_, _Inventory Service_, and _Shipping Service_.

Microservice orchestration is a coordination pattern where a single centralized component(the orchestrator) acts as the "conductor" of the process. It explicitly directs the workflow, telling each participant service exactly what to do, when to do it and in what specific order. 

The orchestrator component can be placed at different layers of your architecture. 

1. Orchestrator at Microservices Layer(Process/workflow Service)
Orchestration logic is encapsulated inside a dedicated, standalone microservice.
![[Pasted image 20260522233344.png]]
- Build a dedicated service, often called a "Process Service" or "Workflow Service" (e.g., `OrderProcessService`). 
- This service does not own a core domain database, instead, it contains only the workflow engine and business state machine. 
- It coordinates the domain services via internal gRPC or HTTP calls.

2. Orchestration at the Gateway Layer (Edge Orchestration)
Orchestration logic is embedded directly inside the **API Gateway** or a **Backend for Frontend (BFF)** component.
![[Pasted image 20260522234007.png]]
When a client makes a single request, the API Gateway acts as an aggregator/orchestrator. It intercepts the call, fans out requests to multiple downstream internal microservices simultaneously (or sequentially), combines their data payloads in memory, and strips out unneeded fields before sending a clean, unified response back to the client.

### Inner and Outer Architecture
**Inner Architecture:** what happens **inside** the boundaries of an individual microservice.
	Focuses on the internal code design, data structures, and business logic patterns used to build a single, independent service.
**Outer Architecture:** what happens **between** the services and across the global infrastructure platform.
	Focuses on the global environment. It dictates the patterns, protocols, system infrastructure, and operational guardrails required to make dozens or hundreds of independent services work together as a cohesive, reliable system.

While the inner architecture values team autonomy, the outer architecture demands strict **standardization**.
