### Email Protocols
##### 1.Simple Mail Transfer Protocol(SMTP)
![[Pasted image 20260608105546.png]]
Industry standard for sending email.
Used to push messages from your mail client(like Outlook, Gmail) to a mail server, and then from one mail server to another across the internet. 
	Direction: Outgoing
##### 2. POP/POP3(Post Office Protocol, Version 3)
An older protocol used to receive email. Using POP3, the client connects to the server, downloads all messages to the local device and then typically deletes them from the server.
	Direction: Incoming
	Limitation: Difficult to sync between devices(once a device downloads an email, its no longer available on the server for other devices)
##### 3. IMAP(Internet Message Access Protocol)
A more modern protocol for receiving and managing email. Changes made on one device are reflected everywhere because the "master copy" remains on the server. 
	Direction: Incoming

How they work when together ? 
1. Submission(SMTP): Your email client used SMTP to upload the message from your device to your email provider's SMTP server. 
2. Relay(SMTP): Your server looks at the recipient's address. It then uses SMTP again to transfer the email to the recipient's mail server. 
3. Storage: Recipient's server store the mail.
4. Retrieval(IMAP/POP3): When the recipient opens their email app, the app uses **IMAP** (or POP3) to fetch the message from their server. 

#### Email Formats
![[gmail-duplicate-headers.jpg]]
RFC 5322(Internet Message Format-IMF) defines the standard for emails. 
It consist of header fields, a blank line, and the message body.
Lines must end with a carriage return and line feeds(CRLF) and must not exceed 998 characters. 

Components of an email,
1. The Envelope(handled by the SMTP protocol, not defined by RFC 5322)
2. The Header Fields
3. The Body

Message structure,
```text
+---------------------------------+
| Header Fields                   |
| (From, To, Subject, Date, etc.) |
+---------------------------------+
| Line Feed (CRLF)                |  <-- Explicit blank line separator
+---------------------------------+
| Message Body                    |
| (The actual content)            |
+---------------------------------+
```
Header fields are lines composed of a filed name, a colon and a filed body(value). 
Syntax: `Field-Name: Field-Body CRLF`
Filed names are case-insensitive.

Optional fields, 
1. Sender
2. Reply-to
3. Destination Fields(To, Cc, Bcc)
4. Identification Fields(Message-ID, In-Reply-To, References): used for message tracking and threading. `Message-ID` provides a globally unique identifier for the specific message instance. 

The message body is separated from the headers by exactly one empty line(CRLF). 

Ex:
```text
From: John Doe <johndoe@example.com>
To: Jane Smith <janesmith@example.org>
Date: Mon, 08 Jun 2026 11:15:00 +0530
Subject: Project Status Update
Message-ID: <1234567890.foo.bar@example.com>

Hi Jane,

This is the body of the email message. It is separated from the 
headers above by a single blank line. 

Best regards,
John
```

Limitation of RFC 5322 and SMTP protocol,
1. Text Only - Images/PDFs and EXE files can not be send over an email
2. Language barrier - Original RFC 5322 natively limits the body to flat lines of 7-bit US-ASCII text. Languages with accents (French, German) or non-Latin scripts (Chinese, Arabic, Hindi) could not be represented in 7-bit ASCII.
3. Line length limit - SMTP required lines to be no longer than 1,000 characters, which binary data frequently exceeds.
#### MIME - Multipurpose Internet Mail Extension
MIME was developed to wrap non-compliant data into an RFC 5322-compliant format without changing the underlying STMP infrastructure. 
MIME adds a set of new header fields to the RFC 5322 header section. These headers tell the receiving email client how to reconstruct the message body.

Example MIME header fields,
- `MIME-Version`: Signals the message is MIME-compliant. 
- `Content-type`: Defines the data type. (ex: `text/html`, `image/jpeg`)
- `Content-Transfer-Encoding`: Specifies how the data was converted into 7-bit ASCII.

One of MIME's most powerful features is the `multipart` content type. This allows a single email to contain multiple different parts (e.g., a plain text version, an HTML version, and a JPG attachment).

Each part is separated by a **boundary string**—a unique sequence of characters defined in the main header.

#### Email Security Threats
Types of threats,
- authenticity-related threats
	Ex: IP address spoofing or email spoofing to make traffic look like it originates from a trusted source.
- Integrity-related threats
	Ex: MITM attacks, Modifying email database records(SQL injections)
- Confidentiality-related threats
	Data exposure, leaks, and unauthorized viewing.
- Availability-related threats
	Denying access to legitimate resources.
	Ex: DoS/DDoS, Ransomware

#### Solutions for Email's security threats
1. STARTTLS
A protocol command that tells an email server to upgrade an existing, unencrypted (plaintext) connection into a secure, encrypted connection using **TLS (Transport Layer Security)**.

2. S/MIME(Secure/Multipurpose Internet Mail Extensions)
S/MIME is a protocol that provides cryptographic security(digital signatures and encryption) directly to the email message itself.
It uses public-key cryptography. A sender signs an email with their private key and can encrypt the body and attachments using the recipient's public key.

This provides, 
- Authentication: By digital signatures with RSA encryption and SHA-256 hashing. 
- Confidentiality: By encrypting messages with AES-128 with CBC. 
- Compression(to store and transmit the message)
- Email compatibility: Provides the service of converting the raw 8-bit binary stream to a stream of printable ASCII characters.
S/MIME message content types, 
- Data
- Signed Data
- Enveloped Data
- Compresses Data

2. PGP - Pretty Good Privacy
PGP is a data encryption and decryption program used to signing, encrypting and decrypting texts, emails, files and directories. Similar to S/MIME.

PGP provides,
- Confidentiality: By encrypting messages.
- Authenticity
- Integrity : ensure the message content has not been altered. 

3. DNSSEC
DNSSEC adds cryptographic signatures to existing **DNS (Domain Name System)** records to ensure that the DNS data received from a lookup is authentic and unaltered.

This provides,
- Data origin authentication
- Data integrity verification

4. DNS-Based Authentication of Named Entities(DANE)
DANE is a protocol that allows digital certificates (X.509 certificates used in TLS) to be bound directly to a domain name using DNSSEC.
It uses **TLSA** records in DNS to specify exactly which certificate or Certificate Authority (CA) a client should trust when connecting to a service (like an email server). This prevents attackers from using fraudulently issued certificates from compromised standard CAs.

5. SPF - Sender Policy Framework
![[Pasted image 20260608140735.png]]
SPF is an email authentication mechanism listed in a domain's DNS records that specifies which mail servers are authorized to send email on behalf of that domain.
	SPF provides a protocol by which Administrative Management Domain (ADMD) can authorize hosts to use their domain names in the “MAIL FROM” or “HELO” identities.

6. DKIM - Domain Keys Identified Mail
![[Pasted image 20260608140933.png]]
DKIM adds a **cryptographic digital signature** to the header of an email message, linking the message to the sending domain.
The sender's server signs the email with a private key. The public key is published in the domain's DNS records. The receiving server fetches this public key to verify the signature. If the signature matches, it proves the email genuinely originated from that domain and was not altered in transit.

7. DMARC(Domain-based Message Authentication. Reporting and Conformance)
![[Pasted image 20260608141052.png]]
DMARC is a policy framework that builds on top of both **SPF** and **DKIM** to give domain owners control over how their email identity is handled. 
It requires "alignment," meaning the domain in the visible `From:` header must match the domains verified by SPF and/or DKIM. Domain owners publish a DMARC policy in DNS instructing receivers how to handle failures (e.g., `none` for monitoring, `quarantine` for spam folder, or `reject` to block the mail entirely) and requests reports on authentication statuses.

DMARC reporting provides the sender’s feedback on their SPF, DKIM, Identifier Alignment, and message disposition policies. 
Reports include,
- The sender's DMARC policy for that interval. 
- The message disposition by the receiver. 
- SPF result for a given SPF identifier. 
- DKIM result for a given DKIM identifier. 
- Results classified by sender subdomain. 
- The sending and receiving domain pair.
