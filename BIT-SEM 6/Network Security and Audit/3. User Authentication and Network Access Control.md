## Remote User-Authentication Principle
User authentication is the basis for access control and accountability. 
Two steps,
1. Identification: Presenting identifiers to the systems(password, username)
2. Verification: Generating the auth information that corroborate the binding between the entity and the identifier(JWT, Sessions)

#### Means of Authentication
1. Something user know (ex: password, PIN, answers to security questions)
2. Something user have (ex: physical keys, electronic keycards, cryptographic keys)
3. Something user is (ex: static biometrics like fingerprints, facial recognition, retina scan)
4. Something user does (ex: dynamic biometrics - based on personal actions/patterns of behavior)
#### Mutual Authentication
Traditional authentication is one-way. User has to verify themselves to the website. 

Mutual authentication(AKA Two-Way Authentication or `mTLS` when implemented via TLS) is a security process where both parties has to verify each other's identities before establishing connection. 
- The client verifies the identity to the server.
- The server verifies the identify to the client. 

Usually done by both parties presenting cryptographic certificates issued by a trusted CA. 

Why mutual authentication required ?
- Traditional credentials can be stolen
- Eliminating server spoofing(Man-in-the-Middle attacks)
- Replay attacks
- Machine to Machine(M2M) trust(a way to verify automated machines to each other)
- Defense-in-Depth for Zero Trust Architecture

Examples:
1. Microservices
	When service A need to talk to service B, they user `mTLS` to cryptographically verify each other before sending data across the cluster. 
2. FinTech services
	Banks requires FinTech company servers to present a client certificate.
3. IoT fleet management
	Manufacturers burn a unique private key and client certificate into the hardware of each IoT device during production. When the device powers on and connects to AWS IoT Core or Azure IoT Hub, `mTLS` guarantees that only genuine, manufactured hardware can talk to the cloud.

### Replay Attacks
A malicious actor intercepts a valid data transmission(ex: login request) passing over a network, captures it(packet sniffing) and subsequently re-transmit it to the destination system without modification. Because the intercepted message is completely authentic and correctly encrypted, the receiving system is deceived into treating the replayed message as a brand-new, authorized request from the original sender.

Encryption does not prevent replay attacks.
Encryption provides,
	confidentiality(stopping attackers from reading the data)
	integrity(stopping attackers from modifying the data)
But it does not provide **freshness**.

To defeat replay attacks, every single transmitted packet is unique and bound to a specific point in time or a specific handshake session. This can be achieved by, 
1. Cryptographic Nonce
	A nonce is a random or pseudo-random number issued by the server that must be included in the client's response.
2. Timestamp
	Include an explicit, synchronized timestamp within the encrypted payload.
	When a packet arrives, the server decrypts it and compares the embedded timestamp ($T_{msg}$) with its own current internal clock ($T_{now}$).
	If the difference exceeds an acceptable tolerance window (e.g., $\Delta t > 2 \text{ seconds}$), the packet is flagged as stale and discarded.
3. Sequenced packet numbers
	use strictly incrementing sequence numbers or session-specific tokens for each packet sent during a live connection.
### The evolution of secure remote user authentication
when a client wants to authenticate with a server over an untrusted network, a secure protocol must achieve two main things,
1. Confidentiality & Integrity: Done by encryption 
2. Freshness: To prevent replay attacks

**Approach 1 : Authentication Using Simple Symmetric Encryption**
Client(A) and server(B) share a secret master key ($K_{ab}$) beforehand.
Workflow,
	$(A \to B)$ : Slice sends a identity($ID_A$) along with a message encrypted with their shared key: $E(K_{ab} , [ID_{A} || Timestamp])$
Since only Alice and Bob knows $K_{ab}$ , Bob decrypts it, sees Alice's ID, looks at timestamp to ensure it is fresh, and assume it must be Alice. 

Limitations, 
	This works fine for 1 to 1 communications.
	But if the network has 1000 users who all need to talk to each other, every single user has to maintain 999 separate permanent master keys. 

**Approach 2 : Introducing Key Distribution Center(KDC) for Scalability**
To solve the scaling issue, network uses a third-party server called a **Key Distribution Center(KDC)**. Users don't store each others keys, instead they all have exactly one permanent key with the KDC. 

When Alice wants to talk with Bob, Alice asks the KDC to create a  one-time session key($K_{S}$) for them to use. 

Workflow,
1. $Alice \to KDC$ : $ID_{A} || ID_{B}$
	"I'm Alice, I want to talk to Bob"
2. $KDC \to A$ : $E(K_{a} , [K_{S} || ID_{B} || T || E(K_{b} , [K_{S} || ID_{A}||T])])$
	KDC generate a random session key($K_{S}$).
	It sends back a package with Alice's mater key($K_{a}$).
	Inside this package is $K_s$, plus a "ticket" encrypted with Bob's master key ($K_b$) containing the same $K_S$.
3. **Alice $\rightarrow$ Bob:** $E(K_{b} , [K_{S} || ID_{A}||T])$
	Alice decrypts her part, grabs $K_s$, and passes the encrypted ticket to Bob. Bob decrypts his ticket with $K_b$ and extracts $K_s$. Now, both have the session key.

Then They can share encrypted messages.
1. $Bob \to Alice$ : $E(K_{S}, M_1)$
2. $Alice \to Bob$ : $E(K_S, M_2)$

Vulnerabilities,
	If an attacker intercepts the encrypted ticket Alice sends to Bob in Step 3, the attacker cannot decrypt it. However, if that session key $K_s$ eventually expires or gets compromised later on, the attacker can simply **replay** that exact Step 3 packet to Bob.
	Because Bob's ticket doesn't contain a timestamp or a nonce from Bob, Bob will decrypt it, see a valid structure, and assume Alice is trying to talk to him again. Bob will securely connect to the attacker using the compromised key.

**Approach 3 : The Needham-Schroeder Protocol**
To fix the replay vulnerability in approach 2, We add a Nonce into the KDC handshake. 
By forcing Alice to send a completely unique random number ($N_1$) to the KDC, and forcing Bob to challenge Alice with his own unique random number ($N_2$) at the very end, the protocol attempts to guarantee that both parties are live and active _right now_.

Nonce prevents an attacker from replaying old KDC responses to Alice, because the old responses won't match her brand-new nonce ($N_1$).

Workflow,
1. $Alice \to KDC$ : $ID_{A} || ID_{B} || N_1$
	"I'm Alice, I want to talk to Bob, here is my Nonce."
2. $KDC \to A$ : $E(K_{a} , [K_{S} || ID_{B} || N_1 || E(K_{b} , [K_{S} || ID_{A}])])$
	KDC generate a random session key($K_{S}$).
	It sends back a package with Alice's master key($K_{a}$) with Nonce($N_1$)
	Inside this package is $K_s$ encrypted with Bob's master key ($K_b$) containing the same $K_S$.
3. **Alice $\rightarrow$ Bob:** $E(K_{b} , [K_{S} || ID_{A}) || E(K_S,M)$
	Alice decrypts her part, grabs $K_s$, and passes the encrypted part to Bob. Bob decrypts his ticket with $K_b$ and extracts $K_s$. Alice passes the first message along with this. 

In the step two, KDC considers the Nonce sent by Alice.

### Kerberos
Kerberos is a network authentication protocol designed to provide secure authentication for user-to-user and server-to-server interactions over an insecure network. 
It relies entirely on symmetric key cryptography and utilize a trusted KDC(Key Distribution Center).

Problems Kerberos solve,
1. The scaling problem: If every user has to keep a secret key for every other server, managing those keys becomes impossible.
2. Sending passwords over the network in plaintext allows attackers to easily sniff packets and steal credentials. 

Core components of Kerberos,
1. The Client
2. The Application Server - The resource the user wants to access
3. The Key Distribution Center(KDC) - The trusted third-party that coordinates everything. KDC is mainly in two parts,
	1. Authentication Server(AS) - Verifies who you are during the initial login
	2. Ticket Granting Server(TGS) - Issues the specific tickets needed to access individual network services. 

Kerberos Workflow(3-Exchnage Process)
**Phase 1 : Initial Authentication(Getting the ticket to get tickets)**
Employees use their workstation devices to login to their account by entering their username. The workstation contact the KDC's Authentication Server(AS).
Steps,
1. Client machine sends a request to join the network. 
2. The AS lookup Alice in the DB. It finds Alice's permanent master key(derived from her password). AS generate a temporary **"Session Key"** and a **"Ticket Granting Ticket(TGT)"**. It encrypts the TGT using the KDC's own secret key and encrypts the response back to Alice using Alice's master key. 
3. Employee's computer prompt for their password, decrypts the message and extract the TGT. 
Employee is now authenticated to the KDC.

**Phase 2 : Requesting Service Access(Using the TGT)**
Now the employee(Alice) want to access corporate file server(B). 
She doesn't use her password, uses her TGT.
Steps,
4. Alice sends her TGT along with an Authenticator(a packet containing her ID and a current timestamp encrypted with her session key) to the Ticket Granting Server(TGS). 
5. The TGS decrypts the TGT(since it was encrypted with the KDC's key) to verify it it authentic. It checks the timestamp to prevent replay attacks. If everything matches, the TGS issues a **"Service Ticket"** specifically for the file server(B), encrypted using the File Server's secret master key.
**Phase 3 : Presenting the Ticket to the Service**
Alice now directly talks to the server(B).
Steps,
6. Alice forward the Service Ticket and a fresh Authenticator to the File Server(B)
7. The file server decrypts the ticket using its own master key, validate the timestamp inside the authenticator to ensure it isn't an old replayed packet and grant Alice access. 

How Kerberos solved the Needham-Schroeder Replay Flaw ?
The primary vulnerability was lack of freshness check.
Kerberos fixed this fundamental vulnerability by shifting away from complex multi-party nonce challenges and relying heavily on **Timestamps**.

Because every ticket and Authenticator packet contains an encrypted timestamp, an attacker cannot record Step 6 and replay it tomorrow. When the application server decrypts a replayed ticket, it compares the timestamp inside with its current clock. If the packet is older than a specified window (typically 5 minutes), the server flags it as a **stale replay** and immediately drops the connection.

(Note: Because of this reliance on timestamps, Kerberos requires all machines on the network to have their clocks synchronized precisely, usually via NTP—Network Time Protocol.)

### Kerberos Realms
A **Kerberos Realm** is a logical security domain or administrative boundary within a network that defines what a specific Key Distribution Center (KDC) has the authority to authenticate.
Rules,
1. The central Kerberos server(KDC) maintain a database containing the user IDs and cryptographic hashed passwords of all participating users registered inside the specific domain. 
2. Every application server belonging to that realm must be explicitly registered with the KDC and share a unique master key with it.

If a client and an application server belong to the **same realm**, the client can request service tickets directly from its local Ticket Granting Server (TGS) using the standard 3-phase exchange process.
### Multiple Kerberis (Inter-realm Authentication)
This refers to an environment where the network is split across multiple independent Kerberos realms, each managed by its own distinct Kerberos KDC server setup. 

If network A has multiple realms with their own KDCs(A, B, C), a client registered in realm A can not natively talk with realm B.
To allows cross-domain access, Kerberos support Inter-realm authentication.
For this to work, **the Kerberos servers in each interoperating realm must establish a trust relationship by sharing a secret key with each other**.

Workflow: A client from realm A want to access a server in realm B. 
1. **Request Local TGS Ticket:** The client contacts its local KDC (Authentication Server) in _Realm A_ to get an initial Ticket Granting Ticket (TGT).
2. **Request Remote TGS Ticket:** Instead of requesting a ticket for the end service, the client contacts its local _Realm A_ TGS and says: _"I want to talk to the KDC in Realm B."_
3. **Receive Cross-Realm Ticket:** The local TGS issues a special ticket encrypted with the **inter-realm secret key** shared between _KDC A_ and _KDC B_.
4. **Present Ticket to Remote TGS:** The client leaves its home domain and contacts the TGS belonging to _Realm B_, presenting the cross-realm ticket it just obtained
5. **Receive Target Service Ticket:** _KDC B_ decrypts the ticket using its shared inter-realm key. Because it trusts _KDC A_, it accepts that the client's identity has already been verified. _KDC B_ then issues a valid Service Ticket for its local application server.
6. **Access Remote Server:** The client presents this brand-new Service Ticket directly to the target application server in _Realm B_ to gain access.

Kerberos Version 4 shortcomings,
- Encryption system dependence
- Internet protocol dependence
- Message byte ordering
- Ticket lifetime
- Authentication forwarding
- Inter-realm authentication

Kerberos Version 4 deficiencies addresses in Version 5 updates,
- Double encryption
- PCBC encryption 
- Session Keys
- Password attacks
### Federated Identity Management
FIM is a system that allows users to use a single set of credentials(username & password) to access applications and data across multiple, completely separate organizational domains. (like SSO)

Typical services provided by an FIM, 
- Point of Contact
- SSO Protocol Services
- Trust service
- Key service
- Identity service
- Authorization
- Provisioning
- Management

Identity federation is an extension of identity management to multiple security domains. 

Components of a FIM used to execute secure login,
1. The user
2. The identity provider(IdP) - The organization that holds the user’s actual credentials and handles their authentication
3. The service provider(SP) - The external application or third-party company that provides the service the user wants to access. 

Workflow,
1. The user attempts to log into an external Service Provider.
2. Service provider recognizes the user's organization and redirects the user's web browser back to their home company's Identity Provider (IdP) login page.
3. The user logs into their IdP using their standard corporate credentials. The IdP verifies who they are locally.
4. The IdP generates a signed, encrypted digital token (often called an **Assertion** or **Claim**). This token says: _"We have verified this user. Their email is `alice@company.com`, and they are authorized to use your service."_
5. The browser passes this cryptographic token back to the Service Provider.
6. The Service Provider checks the signature on the token using a pre-shared public key from the IdP. If the signature is valid, the Service Provider trusts the assertion and logs the user in—**without ever seeing or storing the user's password.**

Common standards,
- SAML(Security Assertion Markup Language) - An older, XML-based standard heavily utilized in corporate enterprise and B2B environments
- OIDC(OpenID Connect) - A modern, lightweight identity layer built on top of the **OAuth 2.0** framework. Uses JWT tokens.

### EAP(Extensible Authentication Protocol)
EAP is not a specific protocol. It's a authentication framework. 
EAP was created to provide extensibility for Network Access Control systems (like corporate Wi-Fi or VPN gateways using IEEE 802.1X).

Without EAP, if a network device (like a Cisco Wi-Fi router) wanted to support a new authentication method, manufacturers would have to rewrite the router’s firmware entirely.
With EAP, the router acts merely as a **pass-through proxy (Authenticator)**. It encapsulates EAP traffic from the client machine (**Supplicant**) and forwards it straight to a backend **Authentication Server** (typically a RADIUS server). The core validation math is handled at the server, meaning network hardware doesn't need to be replaced when security protocols evolve.

EAP methods,
1. EAP-TLS(Transport Layer Security)
	Uses Public Key Infrastructure (PKI) and Asymmetric Digital Certificates
	It establishes a TLS handshake between the client and the RADIUS server. It enforces strict **mutual authentication**:
	- The server presents its digital certificate.
	- The client also has to presents it digital certificate. 
2. EAP-TTLS(Tunneled Transport Layer Security)
	Uses Asymmetric Encryption for the server, traditional credentials (passwords/tokens) for the client. 
	This bypass the administrator overhead to issue digital certificate to thousands of users. 
	Workflow,
	- The server presents its digital certificate to the client. An encrypted TLS tunnel is established between them.
	- Inside this securely encrypted tunnel, the client passes regular, low-cost credentials (like a standard corporate username and password) to the server.
3. EAP-GPSK(Generalized Pre-Shared Key)
	Uses Symmetric Key Cryptography.
	A lightweight method designed for resource-constrained or automated devices (like IoT hardware).
	Uses a pre-shared secret key known by both the peer and the server to execute a fast, mutual authentication handshake and derive session keys.
4. EAP-IKEv2(Internet Key Exchange version 2)
	Uses IPsec-native protocols (Symmetric, Asymmetric, or Hybrid credentials).
	Imports the handshake payloads and security mechanisms from **IKEv2** (the foundational protocol used to build modern IPsec VPN connections) directly into the EAP framework.
